## 一、受众面进订阅规则

### 1.1 它是收窄条件，不是"再多命中一档"

订阅规则原有三项（关键词 / 领域 / 机关）是**或**的关系：任一命中即相关，
回答的是"这条跟我有没有关系"。受众面回答的是另一个问题 ——"这类公示是不是给我看的"。
两者不是同一种问法，所以新加的这一栏是**并且**：

```
命中条件 = （关键词 ∨ 领域 ∨ 机关） ∧ 受众面 ∈ 勾选的那几档
```

顺序写错了会静默发错信，所以两处顺序都是有意的：

1. **收窄判在 `scope='all'` 短路之前**。"订全部新公示 + 只看公众广域"要的是
   *全部里的公众广域那一批*；把受众面判在短路之后，这个人会收到全部，
   而表单上明明写着"勾了就只发这几类" —— 那是界面在撒谎。
2. **只勾受众面是一条完整可用的订阅**（`hasAnyRule` 收下它、匹配时返回 `true`）：
   "这类公示我都要"是一个说得出口的意图，也正是"立法、税收这类影响面广的我想都看一眼"
   那种用法。漏了这一支的后果不是报错，而是这条订阅**永远收不到信**。

判据都在 `src/lib/subscription.ts` 的 `matchesAudienceFilter` / `hasAnyRule` /
`validateSubscriptionRules` 三个纯函数里，提醒任务与新公示通知共用同一份（#60 定的同源规矩）。

### 1.2 「未判定」刻意不能订

订阅表单只给两档（公众广域 / 行业专业），**没有"未判定"**。理由是它不是一个意图：
没有人会说"请把你们没归好类的那批发给我"；而想全都收的人本来就**什么都不勾**（空 = 不限）。

为此 `audience.ts` 里把"可筛选"与"可订阅"两份清单分开，并且**后者是前者的子集**（前者由后者
拼出来，避免两份清单各写一份后漂移成"筛得到但订不到"）：

| 清单 | 取值 | 用处 |
| --- | --- | --- |
| `NOTICE_AUDIENCES` | public / sector / **unknown** | 列表页筛选（未判定是运营要筛的那一批） |
| `SUBSCRIBABLE_AUDIENCES` | public / sector | 订阅规则（**不含 unknown**） |

**未判定（含本列上线前的 NULL）不算任何一档**：勾了受众面的订阅收不到它们。
不这么做的话，"公众广域"这个名字会开始混进技术标准与行业规程，而那个名字本身就是给读者的承诺。
现场代价是 2 条（分布式数字身份 / 水俣公约添汞产品）—— 不勾的人不受影响，这是已知且可接受的边界。

### 1.3 读侧遇到白名单外的值：丢掉（放宽）而不是保留（收死）

`safeParseAudiences` 只认这两档，读到别的值一律丢掉。两条路各有一个坏结果，选的是**可见**那个：

- **丢掉未知值** ⇒ 这一档收窄失效 ⇒ 订阅者**多收**几封（他会发现，我们查得到）；
- **保留未知值** ⇒ 这个条件永远不命中 ⇒ 他**一封都收不到**且没有任何报错。

受众面是收窄条件，放宽是安全方向，收死不是。取值只可能从本站表单来（路由按白名单过滤），
所以走到这里说明分类体系被改过名 —— 那时该做的是一次显式迁移，而不是让读侧悄悄表达旧语义。

### 1.4 落库、表单与确认流

- **迁移 `0018_add_subscription_audiences`**（双方言）：`subscriptions.audiences_json`，
  `NOT NULL DEFAULT '[]'`。**默认空数组 = 不限** ⇒ 存量订阅与旧版**逐条一致，零回填**
  （选 `NOT NULL` + 默认值而不是可空列：可空会让读侧多出一条"到底是没设还是解析失败"的歧义）。
- **四条写入路径共用一份**（`ruleColumns` / `serializeRules`）：新建 / 待确认改动 / 确认套用 /
  读回；加一列要记得改三处的教训见 #83 第六节 F 项，这里用同一种结构挡。
- 表单：`audiences` 复选框（两档，`title` 挂口径说明），位置在「订阅范围」之后、关键词之前 ——
  它是对整个规则的收窄，放在"范围"旁边才读得通。文案明写「不勾 = 不限」「与关键词 / 领域 / 机关
  是**「并且」**的关系」。
- 确认邮件：勾了就写一行「受众面（收窄条件，只有这些才会发）：公众广域」；
  `scope='all'` + 勾了受众面时那句"不限关键词 / 领域 / 机关"**必须换掉**，否则是把收窄说没了。
- 管理入口（邮件底部的 token 链接）回填勾选状态，改动仍走"再确认一次"（#60 第 4 刀那套）。

## 二、截止提醒合并成一封

### 2.1 旧行为的现场

旧实现是"一条公示一封"：同一位订阅者同一轮命中 3 条就发 3 封、6 条就发 6 封。
生产实测那一轮（2026-09-25）**同一个人收到 6 封**，站长随后退订。
新公示通知从 #60 第 3 刀起就是"一人一封汇总"，提醒这一侧一直没跟上。

### 2.2 口径

- **一人一封**：按订阅者收齐本轮到档条目，按剩余天数**从少到多**排（最急的排最前），
  一封发出。判据（条目 × 档 × 订阅）与去重标记**一个都没动** —— 合并的是**信**，不是规则。
- **只到档 1 条时仍走单条那封**（`buildReminderEmail`）：它已有生产样本、文案被单测逐字钉着，
  没有理由为了形式统一去改动一封正在正常工作的信。
- **每条都保留自己的**截止日期、剩余天数（含补发标注）、站内详情链接、官方原文链接 ——
  合并成"一封里只写标题"就不是减量而是减信息了。
- **上限 20 条**（`MAX_REMINDER_ITEMS_PER_EMAIL`，与 `MAX_NOTICES_PER_EMAIL` 同一个量级与同一条
  理由），溢出的**只报数、不写标记**，下一轮还会带来。**刻意不做成环境变量**：它不是运维要调的
  旋钮，#83 刚清完 7 个"文档说能调、compose 没接线"的幽灵旋钮，不再新造一个。
- **发信失败 ⇒ 一条标记都不写**：这一批同生共死，整批下一轮重来。代价是"整批延迟一天"，
  换来的是不会出现"信没送到却记成已通知"。重复提醒比漏提醒可接受（FOLLOWUPS #51 那条
  at-least-once 口径），而"信没送到却记成已通知"不可接受。
- 订阅承诺那句（信末政策说明）补了一句实话：「同一轮里若有多条同时到档，会合并成一封发出，
  不按条数连发」。**文案里的承诺必须与刚上线的行为一致**，否则它就成了下一页要修的谎。

### 4.3 撞到的事：`npm ci` 不是卡死，是被限速（已修，且从根上修）

包改动（`package.json` 只多了 `pretest` 一行）让 Docker 的依赖层缓存失效，于是这次要真跑
`npm ci`。**它跑了半小时没结束**，看着像卡死 —— 但实测不是：

```
日志停在 #11 56.56s          load average 0.04
npm 进程 rchar=68120 二十秒不涨   磁盘 25G 可用
```

现场量网络才看清原因（同一台机器、同一时刻）：

| 目标 | 结果 |
| --- | --- |
| `registry.npmjs.org/next`（元数据 31 MB） | 跑满 25s 超时，只收到 **3.4 MB**（≈136 KB/s） |
| `registry.npmmirror.com/next` | **1.65 秒** |
| 官方 tarball（1.2 MB） | 8.4s |
| 镜像 tarball | 0.11s（302） |

处置不是"多等一会儿"，而是把源做成**构建期可配**：`Dockerfile.web` / `Dockerfile.worker`
加 `ARG NPM_REGISTRY`（缺省仍是官方源，本文件不假设部署地），`docker-compose.yml` 两个
`build.args` 都转发它，`.env.example` 声明，`docs/deploy.md` 写明；生产 `.env` 追加一行
`NPM_REGISTRY=https://registry.npmmirror.com`（追加前先备份 `.env`，`docker compose config`
实测两个服务的 build args 都解析成镜像源、且配置整体仍可解析）。

**换源不降低供应链保证**：`npm ci` 按 `package-lock.json` 里的 `integrity`（sha512）逐包校验，
镜像站替换内容会当场失败。改完重跑：`npm ci` + 两个镜像构建 + 导出**总计约 2 分钟**建完
（同一台机器、同一份依赖）。

顺带**清掉了一条上一轮的残留**：#83 部署时为了让缓存命中，镜像里那份 `package.json` 是
"少了 `pretest` 一行"的旧版；这次依赖层真的重建过，镜像与仓库逐字节一致了。这条**验过**，
不是推断：宿主机与两个镜像里 `/app/package.json` 的 sha256 都是
`46b5b0f701fccce0aa5f2851b6b0002dbcc34354a90c8bf893a08d197ea395ae`（= 本地仓库那份按
LF 归一后的哈希；本地工作区是 CRLF，那是 `core.autocrlf` 的事，提交进去的都是 LF），
且镜像里 `grep -c '"pretest"'` = 1。另记一条看着小但值得知道的：`docker compose exec worker
npm config get registry` 仍是官方源 —— **构建期参数没有漏进运行时**（`npm ci --registry=…`
只对那一次命令生效），所以换源不影响容器里任何运行期行为。

一处测试本身的教训：给这条转发加的 pin **第一次是假绿灯**——`pattern` 写成了旧的那条
不变量用例（"无断线旋钮"），而它查的是"compose 里出现过 ${VAR}"：两个服务只要还有一个在
转发就照样为绿。改指新加的按服务断言后才真变红。**假绿灯的来源不止"片段写错"，还包括
"指对了文件、指错了用例"**。

## 六、证据边界

- 生产数字（备份体积与 6 项校验、迁移条数、`audiences_json` 的默认值）都是 2026-09-26 现量的；
  只读查询与公开地址抓取的方法写在第四节。
- 存量兼容那句"与上线前逐条一致"是**结构上的**：默认 `'[]'` 让 `matchesAudienceFilter` 直接
  返回 `true`，与没有这一栏时同一条路径；单测里有一条专门钉这个（`空数组 = 不限`）。
- "6 封 → 退订"这条因果是**时间相邻 + 他的原话**（"订阅信息有点多"），不是实验结论；
  但即便不是唯一原因，减少同一人的连发在这条路径上也没有反面代价。
- 这一轮**没有**动摘要投入（#83 第七节第 1 项）与摘要重跑（第 4 项）：两者都等"摘要模板下一次
  要改时"，条件仍未满足。
