## 一、这一轮要解决的问题

按 issue #59 的功能缺口清单，转化漏斗的**末端**是四件事凑不齐：
不能按机关订阅（G4）、没有「新公示」通知（G5）、提醒档位按精确天数命中所以停摆一天就永久
丢档（G6）、没有改规则的入口（G7）。分刀做，每刀单独可上线。

## 二、第 1 刀：提醒不再静默丢档（G6）

`worker/jobs/send-deadline-reminders.ts` 原来这样选档：

```ts
const stage = REMINDER_DAYS.find((entry) => entry.days === days);
```

调度是每日一轮（生产 `WORKER_INTERVAL_MS=86400000`），所以只要那一天任务没跑成
——发布窗口错开、容器重启、某个慢源把整轮拖过宽限期——条目就从「剩 8 天」直接跳到
「剩 6 天」，7 天档**永远不会再命中**。用户少收一封提醒，日志里没有任何异常，
第二天也不会有告警：这是最糟的一类缺陷（静默、单向、不可事后察觉）。

改成 **窗口 + 已发标记**（`pickDueStage`）：

- 已到该档（`剩余天数 <= 档位天数`）且该档没发过 ⇒ 本轮发它，漏掉的那天下一轮补上；
- 两档都待发时只发更靠前的那档 ⇒ 每轮每人每条至多一封，补发不会变成轰炸；
- 去重键仍是「条目 × 订阅 × 档」⇒ 每档至多一封这件事没有变弱；
- 选档**按订阅**判定（不能按条目算一次给所有人用）：甲可能早在 7 天前就收到过，
  乙是中途才订阅的，同一条目上两人状态不同。

窗口化会新引入一个坑，一并挡掉：库列 `status` 是抓取口径的缓存（issue #43 的既有事实），
已过截止但还没被下一轮抓取改口的条目仍是 `open`；按窗口判定就会给"已经截止"的条目发提醒。
`remainingDays < 0` 直接不发。

措辞跟着改：补发的那一封不能自称「截止前 7 天提醒」却写着"还剩 5 天" ——
`buildReminderEmail` 现在在 `实际剩余 ≠ 名义天数` 时标「截止前 7 天档补发（原定提前 7 天，
实际剩 5 天）」，主题与正文都按**实际剩余**说。订阅页与邮件里的固定承诺那句也改成可兑现的说法
（「漏跑的那天下一轮补发一次，不会重复发」）。

## 三·补 第 2 刀：按发布机关订阅 + 「订全部新公示」

`subscriptions` 加两列（迁移 0012，双方言）：`agencies_json` 与 `scope`。

- **机关匹配按参与机关逐个精确相等**：联合发文（`司法部、中国民用航空局`）的每一个参与
  机关都能单独命中，与 issue #21 的列表筛选同源；**不做子串** —— 订「司法部」不该收到
  「司法部办公厅」。机关名两侧都走 `canonicalAgency`，否则会出现
  「用户订了中国民航局、条目写的是中国民用航空局」这种永远对不上的订阅。
- **候选清单来自库里实际出现过的机关**（`listNoticeAgencies()`），不写死一份 —— 写死的必然过期。
  提交侧**不做**"必须在候选内"的白名单：某个新部委第一次出现时，正是用户最想收到的那条。
- `scope='all'` 必须是**显式选的**（表单里一个单选，放在条件之前）。刻意不采用
  「规则为空就当订全部」：空规则更常见的原因是漏填，把漏填解释成"要全部"，
  用户是在收了一堆邮件之后才发现自己没设过条件。反向的守卫也要有：
  空条件 + 没选全部 ⇒ 拒绝。
- 三条写入路径（新建 / 已确认改规则 / 待确认改规则）合并成一个 `ruleColumns()`。
  这不是整理代码：漏掉一处就是"重新提交一次订阅，机关规则被静默清空"。
- 截止提醒与新公示通知共用 `matchesSubscriptionRules`，单测里有一条源码断言盯着
  任务不许自己再写一份关键词匹配 —— 分家的表现是「我明明订了却收不到」，不报错、无日志。
