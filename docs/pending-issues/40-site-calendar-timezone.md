# 「今天」按进程时区算：生产容器跑 UTC，北京时间凌晨那 8 小时里倒计时、状态与点击日归属全错一天

## 审计结论（2026-09-21）

| 检查项 | 结论 |
| --- | --- |
| 容器时区 | **缺陷根源** —— web / worker 都跑在 UTC（compose 与 .env 里都没有 `TZ`），宿主是 CST；而全站日历口径按进程时区算 |
| 倒计时 / 状态推导 / 按日点击 / 截止提醒 / 统计月窗口 | **缺陷**（同一个根因，见下） |
| 工信部列表 `endtime` 时间戳的切日口径 | 结果正确、**注释写错了理由**（见「附带复核」） |

## 缺陷：日历口径是数据的性质，却挂在部署环境上

这些公示全部来自中国国家级机关，「2026年9月21日前反馈意见」指的是**北京时间**
9 月 21 日 24:00。而 `src/lib/dates.ts` 的 `localDateIso()` 取的是**进程时区**的日历日
（`getFullYear()/getMonth()/getDate()`）。实测：

```
宿主机 date            → Mon Sep 21 13:41 CST 2026
docker compose exec web date  → Mon Sep 21 05:41 UTC 2026   （TZ 为空）
```

于是北京时间 00:00–08:00 这 8 小时里，服务器认为「今天」还是昨天：

1. **倒计时多一天**：今天截止的条目显示「剩 1 天」而不是「今天截止」；刚过期的条目
   仍显示「今天截止」并留在进行中列表；
2. **状态推导错一天**：`crawl-notices.ts` 的 `deriveStatus` 用 `deadlineAt < localDateIso(now)`
   判「已截止」，落在该窗口的抓取轮次会把刚过期的条目继续标成「征求意见中」；
3. **北极星指标的日归属错一天**：`recordOutboundClick` 按 `click_date = localDateIso(new Date())`
   落库 —— 北京凌晨那 8 小时的点击全记到前一天（统计页按日聚合、Top 榜口径随之偏移）；
4. **截止提醒（d7 / d3）**：`send-deadline-reminders` 用 `daysUntil`，同样错一天；
5. **统计页趋势窗口左移一个月**：`lastMonthWindow` 用 `getMonth()`，北京时间每月 1 日
   00:00–08:00 会少掉当月、多出半年前那个月。

**最隐蔽的一点是测试路径与生产路径分叉**：e2e 跑在开发机（东八区）、生产跑在 UTC
（CI 默认也是 UTC）—— 本地全绿，线上每天有 1/3 的时间在错。这与 issue #32
（两条搜索实现给出相反答案）是同一类问题：**口径必须由代码钉死，不能靠「本机恰好对」**。

## 修复

`src/lib/dates.ts` 显式按 IANA 时区取东八区日历日（容器内实测 Intl 可正确换算）：

- `siteDateIso(date)` —— 站点日历日 `YYYY-MM-DD`，用 `Intl.DateTimeFormat`
  （`timeZone: 'Asia/Shanghai'`）+ `formatToParts` 逐段取值（不依赖某个 locale 的拼接格式，
  免得换 ICU 版本格式就变；取不到分段直接抛错，绝不悄悄退回进程时区）；
- `siteMonthIso(date)` / `lastSiteMonths(now, count)` —— 月份口径与「最近 N 个月」窗口；
- **改名**：`localDateIso` → `siteDateIso`（名字本身就是那个谎言：它从来不是「本地」的），
  调用点全部跟着改：`go/[id]/route.ts`（日志）、`db/repo/notices.ts`（点击落库）、
  `lib/alerts.ts`（告警去重日）、`worker/jobs/crawl-notices.ts`（状态推导）、
  `app/stats/page.tsx`（趋势窗口）；
- **顺手消掉两份重复实现**：统计页与 `tests/e2e/stats.test.mjs` 各自抄了一份
  「最近 6 个月 / 今天」的实现（都按进程时区）—— 现在两边都调 `lastSiteMonths` /
  `siteDateIso`，口径只有一份；
- **不加 `TZ` 环境变量**：日历口径是数据的性质，不该是部署的旋钮 —— 漏设一次就静默错一天，
  而代码里钉死之后任何环境（开发机 / CI / 容器）都给同一个答案。

## 附带复核：工信部 `endtime` 时间戳的切日口径（结果对，注释错）

`epochMsToIsoDate` 的注释原写「该站时间戳取当日 00:00 UTC，故按 UTC 切日即可」。
实际取线上列表核对：**24/24 个 `endtime` 都落在 16:00 UTC**，即「**截止日次日 00:00
（北京时间）**」—— 那是征集期**关闭的瞬间**：

```
1792252800000 = 2026-10-17T16:00Z = 北京 2026-10-18 00:00 → 显示 2026-10-17
官方详情页正文：「2026年9月18日—2026年10月17日」  ✓ 一致
```

逐条比对：24/24 条库内 `deadline_at` 等于 **UTC 切日**的结果；另抽 4 条与官方详情页
正文核对全部一致。**结论：实现不改**（UTC 切日恰好等于人读的截止日），但注释里的
理由必须改对 —— 否则后人「顺手修正成北京切日」会把全部工信部截止日期推晚一天。
已把真实约定与复核依据写进注释，并加单测钉死这两个值。

## 验收

- 单元（117，新增 6）：`dates.test.mjs` 全部改用**绝对时刻**（带 `Z`）构造 ——
  `new Date(2026, 8, 20, 23, 30)` 是「进程时区的那一瞬间」，同一行断言在 UTC 与东八区
  指的不是同一时刻，那正是缺陷形态；新增跨日/跨月边界断言与「换 TZ 跑子进程」的
  时区无关性测试（`execFileSync` 以 UTC / 东八区 / 纽约 / 基里巴斯分别跑同一函数）；
  `extract-content.test.mjs` 新增 `epochMsToIsoDate` 的钉死用例；
- E2E（170，两种时区都跑）：`stats.test.mjs` 新增「北京 00:00–08:00 窗口」的点击种子
  （用带 `+08:00` 偏移的绝对时刻构造，不受测试机时区影响），按日聚合断言因此能抓住
  「记到前一天」；顺带修掉 Top 榜期望值的兜底排序（原按 fixture key 兜底，与 repo 层
  `orderBy(desc(clicks), asc(id))` 不符，一旦并列就假红）；
- **红检**：把实现退回按进程时区取日期 ——
  ① 开发机（东八区）下「换 TZ 子进程」用例变红（1 项）；
  ② `TZ=UTC`（= 生产条件）下单元 5 项变红；
  ③ `TZ=UTC` 下 e2e 4 项变红（点击日归属与按日聚合）；
- 本地全量：单元 117 + E2E 170 全绿，**开发机时区与 `TZ=UTC` 各跑一轮都全绿**，
  typecheck / lint 干净；
- 线上核验（部署后）：容器进程时区仍是 UTC，但部署的代码返回东八区日历日
  （北京 09-22 00:30 → `2026-09-22`；北京 09-21 23:30 → `2026-09-21`；跨月 →
  `2026-10`；当前窗口 `2026-04…2026-09`）；统计页趋势月份列 `2026-04…2026-09`；
  worker 重建后首轮抓取十源正常、索引 178 条；状态计数 已截止 108 / 进行中 70（= 178）；
  全站页面 200；首页 178 条；详情页倒计时口径正常。

## 未做（有意）

- **不回填历史 `click_date`**：北京时间凌晨那 8 小时的历史点击仍按旧口径记在前一天。
  这是指标数据不是业务数据，回填等于改写历史统计，且无从判断每一行当时属于哪一天；
- **不给容器加 `TZ`**：见上，日历口径写进代码而不是环境变量；
- **`scripts/capture-*.mjs` 的本地日期不动**：那是开发机上的 fixture 抓取工具（令牌按
  当天生成），不参与线上渲染。
