## 一、量出来的东西（先量再改）

### 1.1 段落字数：判读不是被"篇幅"挤掉的，是被**位置**挤掉的

线上《反网络暴力法（征求意见稿）》那条（`0b00deff17dfa050`，真实落库摘要）逐段字数：

| 段 | 字数 |
| --- | --- |
| 这是什么 | 109 |
| 影响谁 | 131 |
| 谁能提 | 36 |
| 草案条文要点 | 617 |
| 改了哪几处 | 445 |
| **可能的争议点（判读）** | **925 ← 全页最大的一块** |

三段 L1 加起来只有 **276 字**，判读本身 **925 字**。所以用户那句"是什么占了主要篇幅"
**不是字数问题**：读者要滚过 `276 + 617 + 445 = 1,338 字` 才看到第一条判读。
（用户的原话是"占用了最开始的主要篇幅"——**首屏**被占，不是字符被占。这个区分决定了做法：
该动的是位置与顺序，不是把 L1 写短。）

### 1.2 「谁能提」的信息量≈0（96 条摘要全量只读扫描）

| 取值 | 条数 |
| --- | --- |
| （空 / 未产出） | **27** |
| 有关单位和公众 | 25 |
| 社会各界 / 社会各界人士 | 14 |
| 社会公众 / 公众（社会公众）/ 公众 | 12 |
| 各机关团体、企事业单位和个人均可提出意见…（4 种写法） | 8 |
| 各有关单位和个人 | 4 |
| 其他 | 6 |

**96 条里 95 条等价于"公众 / 社会各界 / 有关单位都可以提"** —— 而这**本来就是"公开征求意见"的定义**。
平均 10.4 字，去重后 18 种写法全是同义改写（唯一例外是一条适航审定，写的是"填反馈表"的操作要求，
那本该属于「怎么提」）。加 28% 干脆是空的 ⇒ 这一段复述的是一个已知事实。

### 1.3 「影响谁」有价值，但它的价值**只在行业专业档**

| | |
| --- | --- |
| 有值 | **18 / 96** |
| 与标题最长公共子串 ≥6 字（疑似抄标题名词） | **5 条（28%，且这是上限 —— LCS 会把"合法命名标题里的主体"也算成复述）** |
| 行业专业档（84 条）里有值 | 15 条，**条条不同**：「乡镇林业工作站及承担乡镇林业工作的其他机构」「持有国籍登记证书、适航证的航空器所有人或占有人…」「使用压缩气态氢…70MPa 的 M 类、N 类燃料电池电动汽车」 |
| 公众广域档（11 条）里有值 | 3 条，且是**义务主体清单**（平台/学校/监护人）——那是"被管的"，不是"受影响的" |

结论：**「影响谁」在公众广域档没用、在行业专业档是"这条管的就是你"**，而后者页面上没有任何别的东西回答得了。

### 1.4 用户想要的"更深的影响判定"，系统里已经有一份 —— 它在 L3

| | L1 的「影响谁」 | L3 判读自带的「可能受影响」 |
| --- | --- | --- |
| 覆盖率 | 18/96（19%） | **39/39（100%）** |
| 与标题的 LCS | 5/18 达 6 字以上 | 多为 0–1 |
| 例子 | 「道路机动车辆生产企业」 | 「进行批评性报道、爆料的媒体和自媒体账号」「不愿实名发言的用户以及依赖匿名用户的中小平台」「被平台限流、暂停或关闭账号的用户」 |

所以用户说的"加深判定深度"**不是把 L1 的字段写深**（L1 是事实层，提示词明写"宁可留空也不要推断"），
而是**让 L3 承担** —— 它每条都挂着依据的逐字原文，L1 的字段天生没有这个位置。

### 1.5 设计规则：加宽**不许**把正文行拉长

查 `ui-ux-pro-max` 的规则库（两条独立命中）：**Line Length / Container Width** ——
「Limit to 65–75 characters per line」「Limit max-width for text content (65–75ch)」，
反面写法明确写着 **"Full-width text on large screens"**（Severity: Medium）。

换算到中文：舒适区间 25–40 字/行，而改动前 `760px − 40px 内边距 = 720px ÷ 16px ≈ 45 汉字/行`
—— **已经在上限之外**。所以"宽屏上多出来的 700px"**不能用来拉长正文**，
只能用来装别的东西。这条规则直接决定了变体 B 的形状（右栏），也排除了"单栏加宽到 900"那种做法。

## 四、**两个只有渲染才抓得到的缺陷**（本轮最值钱的部分）

这一刀由两个子代理分头实现（页面/CSS 一个、摘要卡/判据一个），两个代理都自证"全绿"：
`tsc` 0、`eslint` 0、新单测在隔离副本里跑通、结构断言全过。**但页面是坏的。**
把本地服务真的起起来截图，一眼就看见主栏被挤成 330px、右栏根本没出现。

### 缺陷 1：右栏被写进了主栏里面

`<aside class="action-slot detail-rail">` 落在 `.detail-main` **内部** ⇒ 栅格只有一个子项 ⇒
右栏退化成主栏中间的一段（窄栏挤在正文里）。

**为什么代理的断言没抓到**：它写的是
`assert.match(grid.inner, /<aside[^>]*detail-rail/)` —— 这只证明"右栏出现在栅格的**子串**里"，
而嵌在主栏内部时子串里当然也有它。**"是子项"与"出现在子串里"是两件事。**
修法：判据换成"把主栏整段抠掉之后，右栏还在栅格这一层"，并加一条反向断言
`!main.inner.includes('detail-rail')`。

### 缺陷 2：宽度写在详情页自己的 `<main>` 上，压不过父容器

第一版写 `main.page.detail-page { max-width: 1120px }`，注释里还论证了"特异性 0,2,0 > 0,1,0"——
**论证本身是对的，但前提错了**：根布局把每一页都包在 `<div class="page">` 里（`layout.tsx:67`），
详情页的 `<main>` 是它的**子元素**。子元素的 `max-width` 再大也压不过父容器的 760px。
表现："栅格确实变成两列了，但整页仍被关在 760px 里"，主栏只剩 `760−40−320−28 = 372px`。

修法：加宽作用在**外层** `.page` 上，用 `:has()` 精确命中"里面装着详情页栅格"的那一层：
`.page:has(.detail-grid) { max-width: 1120px }`。
并且**把两栏切换与加宽绑在同一个 `:has()` 上**：不支持 `:has()` 的浏览器两条都不生效 ⇒
页面与改动前逐字一致（760 单栏）；若只门控加宽、两栏另写一条独立规则，降级形态就是
"760px 容器里硬塞两列"那种挤扁的错版 —— **比不支持更坏**。

### 教训

- **"节点存在" ≠ "结构正确"**；结构断言要证"父是谁"，不是"在不在那一段里"。
- **CSS 的层叠能算，DOM 的层数不能假设**：写 max-width 之前先问"它的父容器是谁、多宽"。
- 这两个缺陷 `tsc`/`eslint`/单测/e2e 全都抓不到 —— **只有把页面真的渲染出来才看得见**。
  这一刀之后，详情页的验收多了一件工具（见下）。
- **代理自报的"可见痕迹"数字也会错**：它把 e2e 里"各段引用块"的数量从 6 改成 5，理由是
  "删了「谁能提」少一个"。实际是 **4** —— 少掉的两个**原因不同**：「谁能提」是整段被删，
  「影响谁」是**没删但被受众面门控挡掉**（那条 fixture 判 public，而它只在行业专业档渲染）。
  这条是 `npm test` 当场抓住的，改的时候把两条原因分开写进了注释。
- **测试 helper 的粗糙处会伪装成"页面错了"**：`topLevelDivCount` 只按 `div` 的嵌套算深度，
  右栏是 `<aside>`，于是它里面那些 div 被数成栅格的直接子项（数出 2、期望 1）。
  修法是"先把右栏抠掉再数"，并把这条粗糙处写进注释 —— 否则下一个人会去改页面。

## 七、第二刀的规格（「影响点」1+2+3，用户 2026-10-02 已拍板）

### 7.1 用户的三条要求（原话）

1. 每条判读里那行"受影响主体"要**简要**（现在是「可能受影响：<长串>」）
2. **块首一行概览**
3. 新增"**受影响的方面**"（区别于"谁"）：如「不愿实名发言的用户 · 匿名发声空间」

### 7.2 现状（2026-10-02 只读实测）

39 条判读的 `who` **覆盖率 100%**、长度 3–29 字、与标题最长公共子串多为 0–1（即不是标题复述）；
但形态不统一（「实验室」3 字 ↔ 「发生或可能发生个人信息安全事件的小型个人信息处理者及受影响个人」29 字），
且存量行**没有** `point` 字段。

### 7.3 提示词（`src/lib/adapters/openai-compatible-llm.ts` 的 SYSTEM_PROMPT）

| 字段 | 约束 |
| --- | --- |
| `quote` | 不变（逐字原文，反查不过整条丢弃） |
| `who` | **≤20 字、单一主体类别、最多一个顿号** —— 禁止罗列三四个主体（那正是用户说的"笼统"） |
| `point` | **新增，≤12 字**：受影响的**东西/方面**，不是主体（「匿名发声空间」「纠错渠道」「合规成本」） |
| `text` / `kind` | 不变 |

反例必须写进提示词：❌「网络服务提供者、网络平台服务提供者、互联网用户公众账号生产运营者、学校、未成年人监护人」；
✅「平台 · 合规成本」。写不出来就留空串，**不许为了填满而编**（沿用既有口径）。

### 7.4 落库与读侧容错

- `QuotedImpactPoint` 加 `point: string`（`src/lib/summary-content.ts`）
- `parseStoredImpacts`：旧行没有 `point` ⇒ 退回空串（**存量不重跑也能渲染**，只是没有"方面"那一半）
- **不因长度拒绝**：格式约束靠提示词；超长值照实显示（不静默丢真内容），但在验收脚本里报出来当提示词迭代信号

### 7.5 渲染（`src/app/_lib/summary-view.tsx`）

```
[可能被规避或滥用] 影响：自媒体账号 · 匿名发声空间
「检举」「舆论监督」未界定认定标准，批评性爆料易被主张豁免而规避治理。
「依法通过网络检举…不适用本法。」查看原文↗
```

- `who` 与 `point` 用 ` · ` 连接；只有其一时只显示其一；**都空则不显示这一行**
- 块首概览（**程序聚合，不额外调模型**）：`共 6 处：2 处可能的不利后果 · 2 处可能被规避或滥用 · 2 处新增的义务或成本`
  ＋ `影响：自媒体账号、平台、实名用户`
  - **类别顺序固定为 `risk → loophole → burden → other`**（就是枚举 `IMPACT_KINDS` / `IMPACT_KIND_LABELS`
    的声明序），**与判读在数组里的先后无关** —— 这一行是拿来**跨条目对照**的，
    顺序跟着输入漂就没法对照了。初稿的示例句写成「可能被规避或滥用」开头，那只是随手举的例子，
    不是顺序契约；实现与测试都按声明序，**doc 与页面不许各说各话**（这一族偏差本项目已经栽过多次）。
- 判据抽 `.ts` 纯函数：`impactOverview(impacts)` → `{ countsByKind, topWho }`，放 `src/lib/impact-display.ts` 同族
  （`topWho` 去重后最多列 4 个、超出写「等 N 类」——**用户 2026-10-02 拍板 4 个**，
  实现成具名常量 `IMPACT_OVERVIEW_WHO_MAX`，免得下一轮改的人去猜这个 4 是哪来的）

### 7.7 存量怎么办（**用户 2026-10-02 拍板：方案 B**）

> 拍板结果：**只重跑「公众广域 + 未截止」**（一次生产写入，已授权）。
> 执行顺序不能反：重跑要用的是**新提示词**，所以必须先部署本刀的代码、再重跑 ——
> 反过来的话，重跑出来的还是旧形状（只有 `who`、没有 `point`），等于白欠一次境外调用。
> 这一条正是"先部署后重跑"的原因，不是流程洁癖。

| 方案 | 范围 | 成本 | 效果 |
| --- | --- | --- | --- |
| A. 不重跑 | 0 | 0 | 存量 39 条只有"谁"没有"方面"；旧的 29 字那种照实显示 |
| B. 只重跑公众广域 + 未截止（**倾向**） | 待量（约 3 条） | 几条调用 | 读者实际会看到的那几条都是新形状 |
| C. 全量重跑有判读的条目 | 约 30+ 条 | 30+ 次境外调用 | 全部统一；但每跑一次都欠着境外通道的合规债 |

**已知代价（写在这里，别让下一个人当 bug 查）**

1. **范围外旧行的概览主体行会读成一句连写**：`影响：A、B、C` 用顿号连，而旧 `who` 自己就带顿号
   （线上 `0b00deff17dfa050` 那条：6 个主体显示成 4 个 + 「等 2 类」，看着像一串没分隔的长句）。
   这是**方案 B 的已知代价**（过期条目不在重跑范围内），不是渲染错 —— 重跑过的 3 条都干净。
   要不要给概览换分隔符或加长度门，是**另一刀**的视觉决定，本刀没自作主张。
2. **`stub-llm.ts` 的 `point` 是空串**：本地 `LLM_PROVIDER=stub` 的路径只渲染「影响：<主体>」那半句。
   代价是 stub 路径看不到 ` · 方面`；好处是它走的正是**存量 39 条的真实形状**（读侧容错天天被走到）。
   要改是一行，但会动到既有 e2e 的固定文案。
3. **`summary-view.tsx` 的注释里还留着「可能受影响：」这个词**（说明改了什么），
   页面 HTML 里已经没有它 —— 验收脚本若按"源码里 0 次"去核，会误报一次。
