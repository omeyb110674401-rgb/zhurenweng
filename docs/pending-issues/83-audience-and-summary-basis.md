## 一、受众面（第 3 件）

### 1.1 它和领域标签不是一回事

领域（`categories.ts` 的 10 个）回答"这是关于什么事的"，受众面回答"**该谁来看、该谁去提意见**"。
两者正交：一条《水法（修订草案）》既是「立法与司法」也是「公众广域」；一条《城市绿地设计标准
（修订征求意见稿）》可能是「生态环境」，却是「行业专业」—— 后者才是读者"我要不要点进去"的判据。

**判据口径是「谁该去提意见」，不是"谁会被影响到"**（这句话写在 `src/lib/audience.ts` 的头注里，
它是这个分类最容易被误读的地方）：一份《电梯安全技术规程》影响的当然包括每个乘电梯的人，
但**能对它提意见的是特种设备生产、维保与检验单位**，所以判「行业专业」；反过来
《道路交通安全法（修订草案）》的技术细节同样只有专业人士说得清，但它是法律、面向全体道路使用者
征求意见，判「公众广域」。

### 1.2 判据与优先级（`src/lib/audience.ts`）

顺序即优先级：**人工覆盖表 → 立法 → 税收 → 民生 → 行业（技术 / 管理 / 领域词 / 名单）→ 未判定**。

顺序换一下就会错判，最典型的两个真实标题：
「公路法（修正草案征求意见稿）」含专业领域词「公路」、「城市道路照明设计标准」含「道路」——
先判行业会把**一部法律**判成行业文件。

三条刻意的不兜底 / 不误伤：

- **判不出来就是 `unknown`**（与体裁判定同一条规矩）。生产 192 条里有 **2 条**落在这一档，
  都留着：分布式数字身份、水俣公约添汞产品 —— 它们是"宁可不判也不硬塞"的现场。
- **「办法」里的"法"字不算立法**（负向断言 `(?<![办方做想用说合])法`）：否则《售电公司管理办法
  （公开征求意见稿）》这种行业规章会被整批推给公众。
- **民生词表刻意不含「食品」「消费」「供水」「燃气」**：它们会命中《婴幼儿配方乳粉…注册现场
  核查要点》（对生产企业）与《城镇供水…技术标准》（对水务单位）。宁缺勿滥，判不准就落未判定。

**人工覆盖表**（`AUDIENCE_OVERRIDES`）现有 3 条，每条都写清理由 —— 规则表管"大多数"，
覆盖表管"我核过的这一条"，两者分开回归测试才钉得住：

| 条目 | 规则会判成 | 覆盖成 | 为什么 |
| --- | --- | --- | --- |
| `954dcc17` 内外贸产品同线同标同质 | 行业专业 | 公众广域 | 面向消费者与市场主体，不是行业技术执行者 |
| `61323da4` 教育系统内部审计工作规定 | 公众广域 | 行业专业 | 读者是系统内审计人员，不是家长与学生 |
| `c81057ef` 食品安全**抽检计划**建议征集 | 公众广域 | 行业专业 | 征集的是检验检测机构与专家的意见，不是面向消费者的食品规定 |

### 1.3 落库、筛选与角标

- **迁移 `0016_add_notice_audience`**（双方言）：`notices.audience` + `audience_basis` 两列。
  落列而不是渲染时现算，是因为列表页要**按它筛选并分页**，筛选与计数必须走同一条 SQL。
- **入库即判**（`upsertNotice`，判据只看标题与来源 —— 两样入库时就齐了，所以**不需要**体裁那套
  "证据强弱"机制，回填脚本也因此没有 `--force`）。
- **回填**：`scripts/tag-notice-audience.mjs`（默认 dry-run，`--apply` 才写库）。
- **核对**：`scripts/audit-notice-audience.mjs`（全库逐条打印判定与依据 + 依据命中分布）。
- **读者侧**：列表页新增一排 chips（全部 / 公众广域 / 行业专业 / 未判定，`?audience=…`，
  「未判定」也留在条上 —— 筛出没归类的那批正是逐条改进规则的入口）；详情页在体裁角标旁多一个
  受众面角标，判据挂在 `title` 上（悬停可核对）；口径摘要、隐藏表单字段、子 feed 三处都带上它。
- **未判定筛选连 NULL 一起收**（`is null or = 'unknown'`）：对运营口径来说，本列上线前的存量
  NULL 与"判过了没线索"是同一件事。这是**唯一**一处把两者合并的地方，别处都分开。

### 1.4 一条被新 e2e 当场抓到的真缺陷

`src/app/feed.xml/route.ts` 的 `feedSearchParams()` 有一份**白名单**（只取首页筛选认的那些键，
`sort` / `page` 到此为止）。加了受众面之后如果忘了往这份白名单里加，表现是：
页面筛选正常、`?audience=sector` 的**子 feed 却是全量** —— 没有任何报错，读者订阅到的
比页面上看到的多。新 e2e 里那条「公众广域的条目不该出现在行业专业的子 feed 里」当场变红，
修法是白名单补一项。这正是"链条中间断一环、两端各自看起来都正常"那一族
（#68/#70 的教训），也是把断言写成**跨端点**（页面条件 vs feed 内容）而不是只测本端的原因。

### 2.2 分类的形状（`src/lib/summary-basis.ts`）

三条**正交**的事实，不许混成一条：

1. **依据**（`basis`）：`attachment-points` / `attachment-no-points` / `attachment-unused` /
   `attachment-unreadable` / `notice-only` / `not-probed`；
2. **模板**（`template`）：`current`（有编制说明要点那一版）还是 `legacy` —— 判据是
   **`explanationPoints` 这个键在不在**（值可以是空数组，键缺席只可能来自旧代码；
   与 #78 那次「键在不在 vs 值是多少」的误报同源）；
3. **可优化性**（`state`）：`已优化` / `未优化（可重跑）` / `未优化（重跑无效）`。

第 3 条是运营唯一能照做的判据，所以它在文案上必须分得开：**把"没有附件可读"的条目排进重跑
队列就是把时间花在不会变的事情上**。

不落库成列：三样都能从既有事实（附件抽取表的行数 / 状态 / `fed_to_summary`，摘要 JSON 的键与
三段数组）当场算出来，而**能算出来的东西存下来就会过期**（#30 的教训）。

### 2.3 顺带修掉一处"页面指着空栏说话"

只要 `draftAvailability` 是 `read-and-used`，摘要卡底部就写"上方「草案条文要点」摘自本站从随文

（那 6 条）—— 于是那行字指着一段根本不渲染的栏位说话。现在 `attachment-no-points` 有自己的一句
实话：「本站已从随文附件里读取到条文（N 份 / 约 M 字），但这份公告属名单 / 打包清单一类，
**没有可逐条摘录的条文**」。

## 五、证据边界

- 本文标"实测"的数字都是 **2026-09-26** 现量的：受众面分层与摘要分层来自生产**只读**查询
  （SQL 与脚本都在仓库里，可复跑）；pin 的 121/121、单测/e2e 计数来自本机跑门。
- **受众面规则的准确性只做到"逐条看过"**：192 条的真实标题逐条对照过三档判定，
  3 条用覆盖表纠偏；剩余误判可能存在（同类里"名字像民生、内容像内务"的条目最容易错），
  迭代方式是"筛未判定 / 看审计脚本 → 登记覆盖表 → 回填"，不是改关键词了事。
- 生成的迁移（0016/0017）在本文写作时**尚未在生产执行**；执行结果记在第六节。
- 用户第 3 件里那句"单独对覆盖面广的公示做细致分析也不消耗很多成本"是**产品判断**，
  本轮没有据此改任何生成逻辑（受众面只作为分类落库与展示）；把它变成"按受众面分级投入"
  需要先有一次量（每条摘要实际花多少时间/调用），登记在第七节。

生产不读它（web 用 `npm run start`、worker 直接 `node worker/index.ts`，两者在两版里都在），

有 `stop_grace_period: 150s` 且当时正在跑一轮，Docker 要等它优雅退出。这段时间里**旧代码仍在服务**
