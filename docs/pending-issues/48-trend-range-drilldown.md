# 趋势表的小计与总计点不开（求和结果缺区间口径）

## 审计结论（2026-09-21）

| 检查项 | 结论 |
| --- | --- |
| **趋势表行小计 / 总计的钻取** | **缺陷（口径缺口）** —— 见下 |
| 首页 `ItemList` / `CollectionPage` | 未做 —— 增强项 |
| e2e 之间共享的小解析工具 | 未做 —— 本会话第四次因「单元格变成链接」改解析器（见文末） |

## 缺陷：统计页最后两处点不开的数字

#36 立下「统计页每个数字都能点开，且点进去的条数必须与表格数字一致」，#45 补齐了
36 个月份格子、#47 补齐了 4 个分布桶 —— 剩下的就是趋势表的**行小计**与**总计**：
它们是**窗口内**（最近 6 个月）的求和，单个 `?month=` 表达不了，所以一直没链。

## 修复

**1. 新增 `?from`/`?to` 区间口径**（YYYY-MM，含两端）：

- 只给一端也有效；
- 两端都给且 `from > to` → **两端都不生效**（手改 URL 把顺序写反是常见事，
  不该因此看到一页「筛选后共 0 条」的假空态）；
- 任一端格式非法 → 该端不生效（与未知领域值同一处理）。

**2. `?month=` 折平为 `from = to` 的别名**：issue #45 已经发布出去的钻取链接保持有效，
而 SQL 侧只有**区间**一条路径 —— 不养两套口径（这一条由既有 e2e 与线上抽查共同守住）。

**3. 统计页**：行小计 → `/?agency=X&lead=1&from=<窗口起>&to=<窗口止>`；
总计 → `/?from=<窗口起>&to=<窗口止>`（零值不链）；页面说明同步更新为「小计与总计点进去
是该区间的筛选结果」。

**4. 仓库层**：`publishedFromMonth` / `publishedToMonth` —— 条件是
`substr(published_at, 1, 7) >= from`（与 `<= to`），与统计页聚合的
`substr(published_at, 1, 7)` **同口径**（口径不一致，条数就对不上）；字符串比较在
两种方言下都按 `YYYY-MM` 的字节序，等价于月份先后，不需要任何日期函数；
`published_at` 为空的行不满足比较 → 与趋势表「缺发布日期不计入」同一口径。

## 验收

- 单元（152，新增 4）：`monthRangeParam` —— 两端合法 / 单端 / 倒置（返回 `{}`）/ 非法端；
  `parseHomeQuery` —— `?month=` 别名折平为 `from = to`、显式区间优先于别名、
  `from`/`to` 计入 `hasFilter`（于是自动继承 issue #41 的 noindex）；
- E2E（183，不变式扩展）：趋势表的**每个非零行小计**与**总计**都必须可钻取，
  链接形态必须是「机关 + `lead=1` + 区间」或「区间」，点进去的「筛选后共 N 条」
  必须等于表格数字，列表页显示区间摘要；
- **红检**：去掉仓库层的区间条件 → 不变式当场变红；
- 本地全量：单元 152 + E2E 183 全绿，typecheck / lint 干净；
- 线上核验（部署后）：**12 个非零行小计 + 总计（128）逐一点开全部一致**；
  `?from=2026-04&to=2026-09` 返回 128 = 表格总计；**别名兼容** —— `/?month=2026-08`
  返回 44 条并显示「发布月份：2026-08」，#45 的 36 个月份格子抽查仍全部一致；
  首页 / 统计页 / feed / sitemap 全部 200。
