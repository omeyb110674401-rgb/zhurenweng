# issue #62：发现层只有一副视角（迭代 5 第 1 刀：排序、只看未截止、最近新增）

对应提交：（第 1 刀）

## 一、这一刀解决什么

issue #59 的迭代顺序表里，第 5 轮（发现层与诚实化收尾）记的缺口是「排序只有一套、索引只三字段」。
落到页面上就是：

- 首页**永远**按「未截止优先 → 截止日期升序」排。想按发布时间看（"最近新出的政策"）
  或者按热度看（"大家都在去提意见的是哪几条"），页面上没有任何入口 —— 只能一页页翻。
- 想只看"现在还能提意见的"，做不到。默认视图里已截止的条目沉底但**仍然在列表里**，
  翻页时它们会占掉一半的屏幕。
- 想只看"这一周新收录的"，也做不到。而 RSS / 邮件提醒的读者恰恰是这个需求最强的一批人。

这一刀把这三件事做成 URL 参数 + 一排普通链接（全站零客户端 JS 的前提不变）。

## 二、做了什么

参数面（`src/app/_lib/home-query.ts`，与 `generateMetadata` 同一份解析）：

| 参数 | 取值 | 不合法时 |
| --- | --- | --- |
| `?sort=` | `deadline`（默认）/ `published` / `newest` / `clicks` | 不生效，回落默认档 |
| `?open=1` | 只看还没截止的 | 只认 `1`，其余等于不带 |
| `?since=N` | 最近 N 天首次收录（1–90） | 不生效（**不夹取**，见下） |

仓储层（`src/db/repo/notices.ts`）：

- `ORDERS`：四档排序的 SQL 实现，`deadline` 档就是原来的 `AGGREGATION_ORDER`，
  **不传参数时一字不差**（首页与所有既有分享链接、统计页钻取链接的行为都不变）。
- `openOnly`：`status='open'` **且** 截止日不在今天之前。
- `firstSeenWithinDays`：`first_seen_at >= 下界`（迁移 0013 加的那列）。

页面（`src/app/page.tsx`、`_lib/notice-item.tsx`）：

- 筛选条上方新增一排「排序 / 范围」入口（`.view-controls`），切换时保留其余维度、页码归 1。
- 排序说明跟着改口：默认档保持原文案「按征求意见截止日期排序，即将截止的排在最前」，
  换档后变成「按提意见最多排序」—— 说明必须与页面真实的顺序一致。
- 列表项加「新」角标（最近 7 天首次收录）。
- 关键词表单把 `sort` / `open` / `since` 一起藏在隐藏字段里带过去。

## 三、几个决定的理由

**`?sort=` 不算筛选（不进 `hasFilter`）**。换排序不改变结果集合，只改变顺序。若算筛选，
`?sort=` 的四个变体全部 noindex，等于把「按最新收录看的这一页」从索引里撤掉 —— 而它
和首页是同一批条目。反过来，`?open=1` 与 `?since=7` 都改了集合，所以都进 `hasFilter`，
也都必须写进「筛选后共 N 条（…）」那行摘要里：少说一个维度，读者就只能猜这个 0 是谁造成的。

**`since` 越界不夹取，而是不生效**。`?since=99999` 的来路是"把窗口放宽到比 90 天更久"，
夹到 90 天给出的是一份**更窄**的结果，而页面看起来正常 —— 读者以为看了全部，实际被切掉一截。
不生效则返回全部条目，那是他所要求的集合的上界。与 `monthRangeParam` 的
「宁可不筛，也不给假空态」是同一条规矩。

**`openOnly` 走展示口径，不走库列**。库里 `status` 是**抓取时**推导的缓存（每日一轮），
刚过截止的条目在下一轮抓取前仍写着 `open`（issue #43 的既有事实）。若 `openOnly` 只看库列，
"只看未截止"这一页就会摆出一条徽标写着「已截止」、按钮还在邀请人去提意见的条目 ——
筛选器和徽标各说一套。判据因此是 `status='open'` **且** `substr(deadline_at,1,10) >= 今天`。

**`first_seen_at`，不是 `fetched_at`**。`fetched_at` 每天被抓取覆盖：拿它当"什么时候进来的"，
全库条目天天都是"新增"。这与 issue #60 第 3 刀（新公示通知）踩过的同一个坑，判据也沿用同一列。
测试里为此特意造了一条「今天被重抓、但 40 天前就进库」的条目（丙），
把判据写错成 `fetched_at` 它就会红。

**窗口用「时刻」而不是「N 个日历日」**。`first_seen_at` 是 UTC 时间戳，而日历日属于东八区：
SQL 里若取前 10 位比日期，边界与页面用 JS 算出的日历日会差 8 小时，同一条既"在近 7 天内"
又不带角标。现在两侧共用 `recencyCutoffIso()` 的同一个下界，规则只有一份实现。
代价是「近 7 天」是滚动的 168 小时而非 7 个北京日历日 —— 对"最近新增"这个用法可接受，
而且不会在半夜跳变。`recencyCutoffIso` 刻意返回 `Date#toISOString()` 的**同形状字符串**：
SQL 侧做的是同形状 UTC ISO 串的字节序比较，形状一旦不同（丢毫秒、带 `+08:00`），
比较不报错、只是给出错的结果。这条由单测钉住。

**排序清单放 `src/lib/notice-sort.ts`，不放仓储层**。`home-query.ts` 的头注写着
「只放纯解析，不碰数据库」。`?sort=` 的白名单要在解析层判，如果 `NOTICE_SORT_KEYS` 住在
`db/repo/notices.ts`，解析层（以及 `generateMetadata`）就会被拖进数据库依赖。
仓储侧的实现则写成 `Record<NoticeSortKey, SQL[]>` 而不是带 `default` 的 switch：
加一档忘了写实现，前者编译不过，后者会静默退化成默认排序（`?sort=` 看着生效，实际什么都没变）。

**每一档末位都强制 `asc(id)`**。#54 的线上事故就是排序不唯一 ⇒ `LIMIT/OFFSET` 在页边界
重复一行、挤掉另一行，而并列在这几个字段上极常见（同轮抓取的批次时间戳相同、点击数大量为 0）。
`clicks` 档尤其明显：绝大多数条目都是 0 次点击。

**「新」角标固定 7 天，不跟 `?since=` 走**。选「近 90 天」时若人人带角标，
这个标记就不再传递任何信息。

**一处已知钉不住的**：`NULLS_LAST`（`published` / `newest` 两档让缺日期的沉底）。
测试跑 SQLite，而 SQLite 的 `DESC` 本来就把 NULL 排最后 —— 撤掉这层 CASE 在 SQLite 下不会红。
它是为 PostgreSQL 写的（pg 的 `DESC` 默认 NULLS FIRST，缺发布日期的条目会冲到"最新发布"首位）。
生产跑的是 pg，所以这层不是装饰；但它只能靠读代码保证，不列入 `check-test-pins.mjs`。

## 四、上线后会看到什么（先把话说在前面）

`first_seen_at` 是迁移 0013 加的**可空列**，且没有回填：仓储层只在**建行**时写入，
更新路径不碰它。所以已上线的存量条目（迁移之前入库的那一批）这一列永远是 NULL，结果是：

- `?since=N` 初期只会列出**上线之后**进来的条目；
- 存量条目永远不带「新」角标。

这是实话（我们确实不知道它们是什么时候进来的），不是坏掉了 —— 与之相对的另一种做法
（拿今天的 `fetched_at` 回填全库）会把 178 条老条目全说成"今天新增"，
一周内页面上人人带角标、`?since=7` 等于不筛。回填那一下换来的是一周的假数据，不值得。

上线后核对（读，不改）：`select count(*) , count(first_seen_at) from notices;`
—— 第二个数应当随每天的抓取增长，若始终为 0 才说明抓取路径没写这列。
