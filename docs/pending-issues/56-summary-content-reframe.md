# 56 · 摘要内容重构为「参与导引」+ 附件解析可行性实测

起因是用户一句判断：**「AI 摘要总结的内容基本都不是实际上的原文。具体条例和信息需要下载或者其他方式获取。」**
先把这句话当成事实去测，测完发现它比"措辞不好"根本得多 —— 于是本轮不是调提示词，而是
改掉摘要承诺的东西（PRD 级别的口径变更），并顺手把一条会诱导编造的字段删掉。
上一轮（#55）的通道与凭据结论仍然有效，本轮只动内容形状。

## 一、先立证据：抓取到的正文里根本没有条文

生产库实测（77 条 `status<>'closed'` 的条目）：

| 测什么 | 结果 |
| --- | --- |
| 正文长度 | **均值 443 字**；76 条落在 **207–1283 字**，只有 1 条例外（6912 字） |
| 带附件清单的条目 | **65/77**（单条最多 11 个附件）；正文里出现「附件」字样的 63/77 |
| 最短的几条 | 「水法（修订草案…）」「道路交通…安全法…」这类**国家级草案**，正文只有 207–216 字 |

也就是说页面抓回来的是**公告壳**：谁、就哪个文件、征求到几号、通过什么方式反馈。
草案全文、标准文本、委员名单都在附件里。

这直接否掉了原来的提示词：它要求「keyPoints：2-5 条，每条概括一个关键条款」，
而输入里没有任何条款可概括。模型只能把壳里的元信息重排成看着像条款的句子 ——
线上实例：`条款1: 公示工业软件标准化技术委员会第一届委员名单`、`条款4: 征求意见期限为30日`，
以及 `条款3: 意见通过电子邮件发送至kjb…` （把「如何提意见」抄进"条款"）。
**这不是措辞问题，是"从空处榨内容"必然产生的伪信息**，再收口提示词也变不出条文，
反而更容易诱导编造。

顺带测出两个质量事实（同一个模型、同一份提示词，两档模型横向对比）：

| 每段平均字数 | glm-5.3-flash（30 条） | mimo-v2.5（28 条） |
| --- | --- | --- |
| 影响谁 | 33 字 | **8 字**（含 1 条空串） |
| 这是什么 | 53 字 | 39 字 |
| 关键条款 | 4 条 / 43 字 | 3 条 / 23 字 |
| 如何提意见 | 127 字 | 74 字 |
| 单次耗时 | 8.2s | 87.6s |

用户选了 mimo 作默认（思考模型把预算花在推理上，输入只有 443 字时看不到收益），
本文件只把数据记在这儿。

## 二、顺手修掉的一个真缺陷：空段能落库

「影响谁」是空字符串的条目**在线上存在**（mimo 28 条里 1 条）：页面上会出现一个标题下面没有内容。
根因是校验不对称 —— `normalizeModelSummary` 对 `keyPoints` 明确拒绝空项，
但 `what/who/howToComment` 只校验「是不是字符串」（openai-compatible-llm.ts 旧 173-179 行），
空串照过。而**后台人工复核表单一直是对的**（缺这三段就退回 `error=missing_fields`）——
同一个形状，两条写入路径两套口径。

改法：三段改为「非空字符串」必填，空串即抛错 → 走既有的重试 / `failed_review` 通路。
新增的两段（谁能提 / 逾期会怎样）**故意不做必填**：原文经常不写，强制只会逼模型编。
单测把「`{"who":""}` 必须抛错」钉住。

## 三、新形状：参与导引

```
what          必填  这是什么（一句话）
who           必填  影响谁（要具体主体，不接受只写「社会公众」）
whoCanSubmit  可缺  谁能提
afterDeadline 可缺  逾期会怎样
deadline      可缺  截止日期（仍回退到抓取值）
howToComment  必填  如何提意见（一句话概述）
channels[]    可空  提交渠道：{kind: email|phone|mail|online|other, value}
（keyPoints 废除；仅保留读旧行的渲染通路）
```

三条实现上的取舍：

- **`channels` 的 value 只放地址本身**，说明文字归 `howToComment`。此前 `howToComment`
  实测最长 185 字，邮箱、电话、邮寄地址邮编、材料要求糊成一坨，手机上看就是一段墙。
- **可点链接保守**：整段是干净邮箱才给 `mailto:`、纯号码才给 `tel:`、整段是域名/网址才给
  `https:`；值里混进说明文字就退回纯文本。**假可点击比不可点击更坏**（点开是错地址）。
- **引用与渠道的配对在去重之前完成**：`normalizeChannels` 会去空、去重、截断到 8 条，
  若先归一化再按下标取引用，后面的渠道会挂上前面的引用。适配器因此**一项都不删**，
  清理统一放在配好引用之后。这条单测钉住（`tests/unit/summary-shape.test.mjs`）。

卡片底部新增一段"条文在哪"的明示，并且**按有没有附件分两种说法**：有附件时指向
下方附件清单，没有附件时（npc 源就不给附件字段）只能说"以官方原文为准"。这一条是
e2e 逼出来的 —— 我一开始无条件写「请从下方附件清单获取」，`sources-aggregation` 与
`npc-pipeline` 三条「无附件条目不应渲染附件清单区」的断言立刻红了：
指向一个不存在的附件清单，跟让摘要假装总结了条文是同一类错。

## 四、旧行为了解析兼容（不是向后兼容的礼节，是重刷窗口的现实）

58 条已生成的旧形状摘要要跑两轮 worker 才换完（每轮上限 50 条、mimo 约 90s/条）。
这期间若 `parseQuotedSummary` 认不出新字段就返回 null，详情页会把它们渲染成
「摘要生成中（待人工复核）」—— **比字段少难看多倍**。所以新字段一律可选、
`keyPoints` 保留渲染通路。已截止条目永不再刷（#4 的既有口径），它们若带着摘要
就长期走这条通路，因此这不是临时垫片。重刷完成后新行不再产生 `keyPoints`。

## 六、B 路线（解析附件取条文）可行性实测

结论：**技术上通，但收益被三件事卡住**，因此本轮不上，数据先存这儿。

服务器侧（生产容器出口，UA 用站点自己的爬虫 UA，串行 800ms，5 源 10 附件）：

| 项 | 实测 |
| --- | --- |
| 可获取率 | **8/10 = 200**，0 超时、0 重定向（final URL 原样，没跳登录页），0.09–3.9s |
| 体积与类型 | PDF 338KB / 524KB / 689KB；DOCX 33KB / 35KB / 2.2MB；老式 .doc 21KB / 113KB。8 个成功体 magic 全对，**没有「200 却回 HTML 壳」的陷阱**（ndrc 的 `content-type` 是 octet-stream，靠 magic 才认出是 docx） |
| 抽出的字数 | mee 的 PDF 60 页 → **50,611 字符**（40,114 汉字、异常符号仅 66、0 空文本页、全档仅 1 图 → 非扫描件）= 公告壳的 **114 倍**；ndrc 的 DOCX → 3,526 字符 = 8 倍 |

三道真正的障碍：

1. **miit 的附件 100% 落在唯一被拦的主机上**。两个 403 都来自 `jyhwzhq.miit.gov.cn`
   （miit 31/32 条附件在这台）。换三种请求头（裸 curl / 浏览器 UA+Referer / 仅 UA）**全是 403**，
   响应体同为 1,335 字的 365cyd CDN 拦截页；家宽 IP 与机房 IP 同样被拦 →
   **既不是我方 IP 信誉也不是请求头，纯 HTTP 无解**。同域名换主机（`www.miit.gov.cn` 的
   filemanager 路径）就 200 且是真 PDF。折算下来约 **16/65** 条带附件的未截止条目拿不到草案本文。
2. **20% 的样本是老式 `.doc`（OLE 容器）**，DOCX 那套 `zipfile` 读 `word/document.xml` 的办法直接失效，
   要再引一个解析器。
3. **附件不保证含正文**：那个 2.2MB 的 caac DOCX 只抽出 **50 字符** —— 它是一张空白意见反馈表。
   所以要有选取逻辑（认「标准文本 / 草案全文 / 办法」这类文件，跳过「意见表 / 回执」），
   并按字数分流决定是否喂模型。

另外未测到、真要做得补上：mohurd / npc / cac / moe / moj 五源的附件表现（本次样本没进）、
扫描件 PDF 的可抽字数、HEAD/Range 行为、以及**给 web/worker 镜像加 PDF 解析依赖**这件事
与 #51 记录的"镜像里装着 devDependencies、容器以 root 跑"叠在一起的成本。

## 七、渠道清单解耦：一处渲染、两个来源

新形状上线后在线上看到的画面是：**同一个邮箱在一屏里出现两遍** —— 摘要卡里一份
（`channels`，issue #55 新增），详情页下方「意见提交方式」块里一份（#27 的确定性抽取）。
两边抽的是同一批地址，第二份出处更弱（模型定位 vs 逐字摘录），却排在更显眼的位置。

线上实测（2026-09-22，首页 15 条详情页，逐字比对两处 `.summary-channel-value` 与
`.channel-value` 的值）：

```
15 条中 7 条已带摘要渠道清单（其余还是重刷前的旧形状，本来就没有 channels）
  ├ 6 条：两处各 2 个值，**2/2 完全重复**（如 zuqiwang@126.com、lilychen@tongji.edu.cn）
  └ 1 条：摘要卡 3 个值、抽取块 1 个值，0 重复 —— 摘要确实补到了程序抽取漏掉的地址
```

所以两边都不是废的：**重复发生在同一条地址被两个来源各写一遍**，而不是某个来源没有价值。
处置因此不是删掉哪一边，而是**解耦**（用户拍板）：摘要继续抽渠道，但**渠道在页面上只有
一个渲染位置**，两个来源合并进同一份清单。

```
mergeSubmissionChannels(程序抽取, 摘要渠道)   // src/lib/notice-brief.ts
1. 程序抽取的排前面、值原样保留，标 source: 'program'
2. 摘要项按归一化值判重（去空白与标点、转小写；长度≥8 时也算包含关系）后追加，
   标 source: 'summary'
3. 摘要项的 quote 落到渠道行的「原文：…」小字上，与程序侧同一位置同一写法
4. 合并后仍受 MAX_CHANNELS=8 约束，不因多一个来源就放宽
```

三处刻意：

- **出处标签强制**：那块标题写着「摘自官方原文，本站未做改写」，摘要定位的地址混进去
  就是冒充原句。标签文字用**「摘要补充」**而不是「AI 抽取」—— 后台人工复核录入的走
  同一条通路，把人的工作标成模型输出也是失真。
- **可点链接在合并侧重新保守生成**：摘要项只有整段是干净邮箱/纯号码/域名才给
  `mailto:` `tel:` `https:`，混了说明文字就退回纯文本（与 §三 同一口径）。
- **包含判重设了长度下限 8**：短串（如传真尾号「6666」）几乎会命中任何地址，不设下限
  会把不相干的两条并成一条。等值判重不受限制。

摘要侧的 `channels` 因此只剩两个消费者：详情页的合并清单，与检索索引
（`search-text.ts` 把渠道值并进可检索文本，模型抽到的地址因此仍可搜到）。
`summary-view.tsx` 里那份渲染连同 `channelHref` 一起删了 —— 保留两条渲染通路就等于
保留下一次重复。

## 八、重刷第一轮的代价：30% 转人工复核，原因集中在一个字段

部署后查库（`select summary_status, count(*), count(*) filter (where channels 非空)`）：

```
done            35  （35 条全部带 channels，新形状）
failed_review   15
pending        135  （其中 108 条是已截止条目，本就不刷；在刷的还差 27 条）
```

worker 日志里 15 条失败**几乎全是同一句**：`摘要输出缺少非空字符串字段 "who"`。
同一条目 `9bd5718592f32ab6` 第 1、2 次尝试都报这个错，第 3 次成功 —— 所以是 mimo 的
输出抖动（偶尔把「影响谁」写成空串），不是那些公示真的没有受影响主体。

这正是 §二 那个修复的**反面代价**：`requiredText` 把「空段落库」改成了「整条作废」。
两个方向都没拍板：

- 把 `who` 降级为可缺段 —— 渲染层现在本来就会隐藏空段（`SectionBlock` 遇空返回 null），
  空「影响谁」已经不再难看，硬要求的收益比 §二 当时小得多；
- 或加大重试次数/退避，把抖动扛过去（代价是单条最坏耗时更长，见 #55）。

已截止条目不受影响（不参与摘要），`failed_review` 的 15 条在后台复核队列里可直接人工填写。

## 九、未做（有意）

- **不给摘要补"条文级"字段**（适用范围/罚则/资质要求等）：输入里没有条文，补字段等于把
  诱导编造从一处变成三处。要做就走 B，先解决 miit 与 .doc。
- **不重刷已截止条目**：#4 的既有口径，它们本来就没摘要。
- **不在摘要卡里重复展示"公示期 / 倒计时"**：页面顶部已有，写进摘要只会挤掉真信息量 ——
  这正是旧 `keyPoints` 的主要产出。提示词里明令禁止复述这类元信息。
- **`SUMMARY_MAX_RETRIES` 与超时不改回 120s**：mimo 87.6s 贴着 120s，误判成本是把好条目送进
  人工复核。代价是单条最坏 4×300s ≈ 20 分钟（记在 #55 的后续表里）。
