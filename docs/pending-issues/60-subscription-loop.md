# issue #60：订阅与通知闭环（迭代 4，分刀进行）

对应提交：（第 1 刀）

## 一、这一轮要解决的问题

按 issue #59 的功能缺口清单，转化漏斗的**末端**是四件事凑不齐：
不能按机关订阅（G4）、没有「新公示」通知（G5）、提醒档位按精确天数命中所以停摆一天就永久
丢档（G6）、没有改规则的入口（G7）。分刀做，每刀单独可上线。

## 二、第 1 刀：提醒不再静默丢档（G6）

`worker/jobs/send-deadline-reminders.ts` 原来这样选档：

```ts
const stage = REMINDER_DAYS.find((entry) => entry.days === days);
```

调度是每日一轮（生产 `WORKER_INTERVAL_MS=86400000`），所以只要那一天任务没跑成
——发布窗口错开、容器重启、某个慢源把整轮拖过宽限期——条目就从「剩 8 天」直接跳到
「剩 6 天」，7 天档**永远不会再命中**。用户少收一封提醒，日志里没有任何异常，
第二天也不会有告警：这是最糟的一类缺陷（静默、单向、不可事后察觉）。

改成 **窗口 + 已发标记**（`pickDueStage`）：

- 已到该档（`剩余天数 <= 档位天数`）且该档没发过 ⇒ 本轮发它，漏掉的那天下一轮补上；
- 两档都待发时只发更靠前的那档 ⇒ 每轮每人每条至多一封，补发不会变成轰炸；
- 去重键仍是「条目 × 订阅 × 档」⇒ 每档至多一封这件事没有变弱；
- 选档**按订阅**判定（不能按条目算一次给所有人用）：甲可能早在 7 天前就收到过，
  乙是中途才订阅的，同一条目上两人状态不同。

窗口化会新引入一个坑，一并挡掉：库列 `status` 是抓取口径的缓存（issue #43 的既有事实），
已过截止但还没被下一轮抓取改口的条目仍是 `open`；按窗口判定就会给"已经截止"的条目发提醒。
`remainingDays < 0` 直接不发。

措辞跟着改：补发的那一封不能自称「截止前 7 天提醒」却写着"还剩 5 天" ——
`buildReminderEmail` 现在在 `实际剩余 ≠ 名义天数` 时标「截止前 7 天档补发（原定提前 7 天，
实际剩 5 天）」，主题与正文都按**实际剩余**说。订阅页与邮件里的固定承诺那句也改成可兑现的说法
（「漏跑的那天下一轮补发一次，不会重复发」）。

## 三·补 第 2 刀：按发布机关订阅 + 「订全部新公示」

`subscriptions` 加两列（迁移 0012，双方言）：`agencies_json` 与 `scope`。

- **机关匹配按参与机关逐个精确相等**：联合发文（`司法部、中国民用航空局`）的每一个参与
  机关都能单独命中，与 issue #21 的列表筛选同源；**不做子串** —— 订「司法部」不该收到
  「司法部办公厅」。机关名两侧都走 `canonicalAgency`，否则会出现
  「用户订了中国民航局、条目写的是中国民用航空局」这种永远对不上的订阅。
- **候选清单来自库里实际出现过的机关**（`listNoticeAgencies()`），不写死一份 —— 写死的必然过期。
  提交侧**不做**"必须在候选内"的白名单：某个新部委第一次出现时，正是用户最想收到的那条。
- `scope='all'` 必须是**显式选的**（表单里一个单选，放在条件之前）。刻意不采用
  「规则为空就当订全部」：空规则更常见的原因是漏填，把漏填解释成"要全部"，
  用户是在收了一堆邮件之后才发现自己没设过条件。反向的守卫也要有：
  空条件 + 没选全部 ⇒ 拒绝。
- 三条写入路径（新建 / 已确认改规则 / 待确认改规则）合并成一个 `ruleColumns()`。
  这不是整理代码：漏掉一处就是"重新提交一次订阅，机关规则被静默清空"。
- 截止提醒与新公示通知共用 `matchesSubscriptionRules`，单测里有一条源码断言盯着
  任务不许自己再写一份关键词匹配 —— 分家的表现是「我明明订了却收不到」，不报错、无日志。

## 三·补 3 第 3 刀：新公示通知（G5 的主干）

截止提醒只在 d7 / d3 两个点发信，订阅者要等半个月才被叫回来一次。这一刀加
`notify-new-notices` 任务：**有新公示收录就发一封汇总**，一人一封。

三条设计口径：

1. **「新」的判据是 `notices.first_seen_at`**（迁移 0013 新增，建行时写入、更新永不覆盖），
   不是 `fetched_at` —— 后者每天被 upsert 覆盖，用它当判据会把三个月前的条目天天重发。
   **存量行留 NULL 且不回填**：NULL = 本次上线之前就在了，一律不通知。这条是
   "刚点确认的老邮箱不会收到库里全部 187 条历史公示"的唯一防线，e2e 直接把它当断言在测。
2. **去重键 =（条目 × 订阅），且写在信真的发出去之后**。先记后发等于把"没送到"说成"已通知"，
   那条公示永远进不了这个人的收件箱。为此给 stub 邮件端口加了 `MAILER_STUB_FAILURES`
   注入（与 `LLM_STUB_FAILURES` 同构）—— 没有注入手段，这类只在失败时成立的保证就只能靠读代码信任。
3. **超出每封 20 条上限的溢出条目不写标记**，下一封再带来；邮件里如实写"另有 N 条本次未列入"。
   写成已通知的话，用户永远看不到它们而我们以为通知过了。

不发信的两条前置：邮件端口不可用（与摘要任务同一口径，说清原因而不是每轮报"任务失败"）、
无已确认订阅。邮件里刻意不提"含 AI 摘要"——新公示的摘要可能还没生成。

## 三·补 5 第 4 刀：改订阅也要再确认一次（解 FOLLOWUPS #52 挂账）

被修掉的行为：已确认的人重复提交表单会**直接改写规则且不发确认邮件**（旧 outcome
`confirmed-updated`）。在只有共享密钥、没有账号的模型里，"知道某个邮箱"于是等于
"能改这个人的订阅"。限流挡不住有意的重复提交，能挡住的是让改动必须经一次确认。

- 迁移 0014 加 `subscriptions.pending_rules_json`（NULL = 没有待套用改动）。已确认订阅再提交时
  新规则进这一列、轮换确认 token、发一封「请确认你的订阅修改」；**确认之前站内生效的仍是旧规则**
  （提醒与新公示通知都按旧规则发，e2e 就是按这个顺序验的）。
- `confirmSubscriptionByToken` 在确认那一刻才套用并清空 pending。这里有个容易漏的点：
  函数原本对 `confirmed === 1` 直接早退，如果保留早退，"改完再确认"这条路永远不生效。
- `confirmTokenStatus` 同样要看 pending —— 否则确认页判定为"已确认"、不渲染按钮，
  用户的改动就卡死在一个没有出口的页面上。
- 新增只读入口 `/subscribe?token=<退订token>`（邮件底部「查看或修改我的订阅」）：预填**当前生效
  与待套用合并后的**状态，并明写"提交后需要再确认一次"。刻意复用退订 token 而不新签一类 token：
  能打开它的人与能退订的人本来就是同一批（能读该邮箱的人），能力面没有变宽，
  而真正的门槛（改动要确认）已经抬起来了。无效 token 按普通订阅页渲染，不报错、
  也不带出任何人的订阅内容。
- 自证门 +3 条（改动不再挂待确认 / 确认时不套用 / 确认页不看 pending），总数 **54/54**。
