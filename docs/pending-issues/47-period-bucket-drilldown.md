# 公示期分布的桶不可钻取（页面上最后一处点不开的数字）

## 审计结论（2026-09-21）

| 检查项 | 结论 |
| --- | --- |
| **公示期分布桶的钻取入口** | **缺陷（口径缺口）** —— 见下 |
| 首页 `ItemList` / `CollectionPage` | 未做 —— 属增强（issue #39 起就记为独立议题） |
| 统计页小计 / 总计的区间钻取 | 未做 —— 需要 `from`/`to` 区间口径（issue #45 记为后续） |

## 缺陷：四个桶是页面上最后一处点不开的数字

issue #36 立下的规矩是「统计页每个数字都应可点开，且点进去的条数必须与表格数字一致」，
#45 补齐了趋势表，#46 修好了桶标签与差额 —— 但分布桶的四个计数仍然是纯文本。

根因不是忘了加链接，而是**桶边界是派生值**（截止日期 − 发布日期）：双方言交集里没有
可移植的天数差 SQL 函数（SQLite 只有 `julianday`，PostgreSQL 直接对 date 相减），
所以 SQL 侧过滤一直做不了（`db/repo/stats.ts` 的注释里写着这条约束），#46 只能先把
「标签对齐边界 + 差额按条数说出」做掉，把钻取记为待定。

## 修复

**1. 桶的定义收到一处**（`src/lib/notice-period.ts`）：key、边界（`minDays`/`maxDays`）
与**页面文案**写在同一条记录里 —— issue #46 的缺陷正是「标签与边界各写一份」导致的
漂移（标签说「30 天以上」、边界其实是 `> 30`，30 落在两个桶里）。现在三处消费同一份：
统计页展示、分布聚合（`db/repo/stats.ts`）、首页筛选校验（`app/_lib/home-query.ts`）。
另外 `bucketOfDays` 在「天数不落在任何桶内」时直接抛错 —— 定义被改坏时宁可当场炸，
也不静默归桶让分布数字对不上。

**2. 唯一一处按驱动分支的 SQL**（`db/repo/notices.ts` 的 `periodDaysExpr`）：

```ts
currentDriver() === 'postgres'
  ? sql`(substr(deadline_at,1,10)::date - substr(published_at,1,10)::date)`
  : sql`(julianday(substr(deadline_at,1,10)) - julianday(substr(published_at,1,10)))`
```

取舍说明（写进代码注释）：宁可写这一处显式分支，也不新增一列存储值 —— 新增列要给
存量条目回填、还要让每条入库路径都维护它（issue #30 的教训：多一个需要维护的字段，
就多一处会与真相脱节的地方）。两侧都先 `substr(…,1,10)` 截到日期部分，与统计页
应用层的日历日差口径完全一致（线上实测两个日期列 100% 是 `YYYY-MM-DD`，这层截断是保险）。
桶条件由 `PERIOD_BUCKETS` 的 min/max 推导，边界仍只有一处定义。

**3. 首页新增 `?period=<key>` 筛选**：严格白名单校验（只认定义过的桶 key），
计入 `hasFilter` → 自动继承 issue #41 的索引口径（筛选视图 `noindex, follow`）；
筛选摘要显示「公示期：16-30 天」（文案取自共享定义）；GET 表单保留隐藏字段。

**4. 统计页**：非零桶的计数链到 `/?period=<key>`；零桶不链（点进去是空态）。

## 验收

- 单元（148，新增 8）：`notice-period.test.mjs` —— **标签里的数字必须与边界一致**
  （把 #46 的坏标签注回去会当场变红）、分桶覆盖 -10~200 全部整数且互不重叠、
  边界值归属（7→lte7、8/15→b8_15、16/30→b16_30、31→gt30）、0 与负天数归最短桶、
  key 校验与文案查询；`home-query.test.mjs` 新增 `periodParam` 白名单与 `hasFilter` 计入；
- E2E（183，新增 1）：每个非零桶的链接只带桶 key，点进去的「筛选后共 N 条」必须等于
  桶数字，列表页出现「公示期：」摘要；零桶不得是链接；
- **红检三层**：① 把标签改成「30 天以上」→ 单测 2 项变红；② 去掉仓库层的桶条件 →
  桶钻取不变式变红（条数不再等于桶数字）；③ 让桶链接分支永不命中 → 同一断言变红；
- 本地全量：单元 148 + E2E 183 全绿，typecheck / lint 干净；
- **线上核验（PG 分支是决定性检查 —— e2e 只跑 SQLite）**：四个桶逐一点开，
  5 / 8 / 105 / 58 **全部与页面数字一致**；桶计数与修复前完全相同；四桶之和 176、
  差额 2 条的说明仍在；列表页显示公示期摘要；首页 / 统计页 / feed / sitemap /
  `?period=b16_30` 全部 200。

## 未做（有意）

- **小计 / 总计的区间钻取**：需要 `from`/`to` 两个参数与对应校验（#45 记为后续）；
- **分布聚合仍在应用层逐行算**：178 行量级，一次分组足够；将来数据变大可直接复用
  `periodDaysExpr` 在 SQL 侧聚合；
- **首页 `ItemList`**：增强项，不是缺陷。

## 本轮反复出现的一个测试坑（记录）

「单元格内容变成钻取链接」这件事在本会话里已经让**三个**测试解析器失效：
#45 趋势表格子、#47 分布桶、以及 #47 里 `notice-brief.test.mjs` 里那份桶解析器的副本。
根因是解析器直接 `\d+` 取数字，而链接的 `href` 里也含数字（`period=b16_30` / `month=2026-08`）。
**规矩：从单元格取数字前先剥标签。** 另外三份重复的解析器也说明 e2e 之间共享一个
小解析工具是值得的 —— 记为后续。
