# 76 — 摘要要"更专业"，先得能分出这是修正案还是新案

## 一、这条的起因（读者视角，2026-09-25）

用户试用后的原话归纳：**摘要对附件条文的分析与对比不够专业、不够全面** —— 多章多节的草案
没有把每一条规定都概括进去；没有结构化展示；附件里的编制说明没有覆盖各个重点要点；
没有对比分析、没有深度分析。并且补了一句关键的区分：**修正案与新案不能同一套做法** ——
修正案只需找到"改了哪些地方 + 影响"，新案才需要另做打算（逐条覆盖）。

先量，再改。三条实测结论决定了后面所有设计：

| 实测（生产 192 条，只读） | 数 | 含义 |
| --- | --- | --- |
| 单份附件正文 中位 / p90 / 最大字数 | 7,476 / 46,902 / 126,018 | 一份附件本身就比窗口大 |
| **超过单份 8,000 字窗口的附件** | **44 / 89 = 49%** | 一半附件被截掉一半以上；p90 只剩 1/6 |
| 一条公示的附件合计超三份总额（24,000 字） | 23 / 55 = 42% | 单次调用装不下"全部条文" |
| 标题含"修正/修订"的条目 | 25 → 分类器实测 52 条判为 amendment | 修正案这一类**今天就有 52 条**，不是将来 |
| 其中有附件正文、且正文含"现行/修改为/增加一条/删去" | 19 / 22 | **官方自带对照内容**，只是没人用它 |
| 附件名里带"对照表"的 | 3 | 信号在正文里，不在文件名里 ⇒ 不能靠文件名判 |
| 有"第 X 条"条款结构的条目 | 约 17，其中 ≥20 条约 9 | 逐条覆盖今天只对个位数条目有效 |
| 标题带被修订标准号（可用于配"上一版"） | 1 | 靠标准号配版本这条路走不通 |

由此定下三条判断：

1. **"逐条都概括"今天做不到不是提示词问题，是输入预算问题。** 一次调用、单份 ≤8,000 字、
   ≤3 份、总预算约 12,000 汉字 —— 在这之上要求"每条都写到"，唯一的生产方式就是编，
   而那正是 #55/#56 花力气删掉的东西。
2. **修正案这一路可以先做，而且更值。** 52 条（覆盖面比"新案逐条"的 9–17 条大）、
   输入天然短（改动点就是那份对照文本）、**不需要多次调用**，
   而且"改了哪几处"逐字取自本站已抽出的正文 ⇒ 可核对的地基一点不动。
3. **"对比分析"要先有基准，而基准不存在。** 同案多轮 0 条（迭代 3 撤销时测的）、
   没有现行法规全文、标准号也配不上 ⇒ 模型若给"与现行制度的差异"，那是外部知识，
   不可逐字核对。所以对比只做**条文 ↔ 编制说明"修改理由"的对照**（两份文本本站都有）。

## 二、本刀做了什么（体裁判定，是"分情况"的前提）

今天全站**没有任何代码在分体裁** —— `attachment-select.ts` 那个按文件名打分只决定
下载哪三个附件，不是体裁。所以先补判定这一层。

- `src/lib/notice-genre.ts`：纯函数 `deriveNoticeGenre({title, attachmentNames, attachmentText})`
  → `{ genre, basis, evidence }`。五类：`amendment / new_draft / package_plan / list_or_result / unknown`。
- **判不出来就是 `unknown`，不兜底成新案**（#9 的领域标签同样没有兜底值）。兜底的害处很具体：
  52 条修正案里若有几条被静默塞进新案模板，表现只是"摘要短了一点"，没人会去查。
- **判定带依据**：`genre_basis`（一句人话）+ `genre_evidence`（证据种类）都入库，
  后台复核队列每条显示"体裁：修正案 ｜ 依据：附件正文含对照措辞「修改为」"。
  这是 #58 删「调度配置」那条规矩的延续：看不出凭什么判的字段，操作者不敢信，也不会去修。
- **弱证据不许覆盖强证据**（`genreDecisionWins`）：最强的证据（正文里的对照措辞）要等
  抽取任务才有，而抓取每轮都会重写标题与附件清单。没有这条规矩，抽取刚把某条升级成
  "修正案（正文级）"，下一轮抓取就按标题把它降回去 —— 两个 job 来回拉扯，读者看到的
  摘要形态天天抖。
- 三个落点：抓取入库时按"标题 + 附件名"判一次（`upsertNotice`，与 `deriveCategoryTags` 同处）；
  附件抽取跑完按"正文"重算一次（`worker/jobs/extract-attachments.ts` 每条公示末尾，失败不带走整轮）；
  存量用 `scripts/tag-notice-genres.mjs` 回填（默认 dry-run，打印分桶与逐条依据）。
- 详情页加**体裁角标**（`genre-badge`，配色比状态徽标淡：它回答"该看什么"，不回答"来不来得及"）。
  判定依据不放公开页 —— 那是给操作者的，读者看到"仅标题证据"只会困惑。
- 迁移 0015（双方言 + journal，`when` 严格递增），三列都可空：
  **NULL = 存量没判定过，`unknown` = 判过了但没线索**，两者都显示"未判定"，但只有前者会被回填脚本再扫。

分类器在生产真实数据上的分桶（同一份函数、真标题、真附件名、真正文措辞）：

```
new_draft 107 ｜ amendment 52 ｜ package_plan 25 ｜ unknown 5 ｜ list_or_result 3
```

那 5 条 `unknown` 是诚实的结果，不是失败：配额分配方案、抽检计划建议、现场核查要点、
委员调整、物种名录 —— 都不属于"改现行"或"新立一部"。它们会显示"未判定"，
将来要么加规则要么继续空着。

## 三、第 2 刀已落地：修正案改动点 + 详情页表格

生产侧这一层已部署并验证（迁移 0015 + 镜像重建 + 回填）：192 条全部判定完，
`new_draft 107 / amendment 52 / package_plan 25 / unknown 5 / list 3`；
修正案里 **27 条靠附件正文（强证据）、25 条只靠标题**。线上详情页确认渲染出角标：
`<span class="genre-badge" …>修正案</span>`。

第 2 刀的形状与判据：

- `QuotedSummary.changes`：每行 `{clause, kind, text, quote, source, sourceUrl}`。
  **引用与内容同在一条对象里**，不用 keyPoints 那种"平行数组按下标配对"（那套吃过错配的亏）。
- 不变量照旧：`quote` 必须能在**本轮喂进去的条文**里逐字反查到，反查不到**整行丢弃**；
  `text` 是模型对着原句写的一句话，本身不可核对，所以页面上绝不让它脱离原文单独出现。
- **覆盖度的分母来自全文**（`listNoticeAttachmentTexts` → `countChangeMarkers`），
  不是喂进去的那一截。拿窗口数分母就是自证：窗口外的改动永远不会出现在"还差多少"里。
  三种写法分开：`complete` / `partial`（照实说"其余不在本站读到的那一截里"）/
  `no_markers`（数到 0 就说没检测到，不写"已列出全部 0 处"）。
- **体裁是真的门控**：`target.genre !== 'amendment' ⇒ summary.changes 一律清空**。
  正文里出现"现行"两个字不等于修正案 —— e2e 专门造了这样一条新案，断言它不长出表格。
- 表格复用既有资产，不新增样式：窄屏滚动容器 `stat-table-wrap`（issue #37 为撑破整页
  那次加的）、表格样式沿用 `stat-table`、出处沿用 `draft-point-source` 的写法。
- stub 按正文原行回响改动点 ⇒ "影子档 / 真档位产出不同"这件事仍可被 e2e 断言，
  档位不会又变回幽灵旋钮（issue #58 的教训）。

测试：单测 414、修正案 e2e 5 条（含"分母等于全文数到的数量"这条）、4 个新 pin
（反查丢弃 / 永远说全部 / 分母 0 也报全部 / 体裁不门控）。

## 三之补：自证门当场抓到一条假绿灯（值得记）

第一版 e2e 里"新案不该长改动点表"这条断言**撤掉体裁门控后仍然通过**，pin 报了红。
原因不在被测代码，在夹具：那份新案正文只有 205 汉字，低于 `MIN_DRAFT_CJK_CHARS = 400`，
于是条文压根没被喂进摘要 —— `changes` 当然是空的，断言测的是"没喂"而不是"闸门"。

修法不是把断言删掉，而是把夹具做长（现 410 汉字），并**把前提写成断言**：
同一条新案必须有 `keyPoints.length > 0`（证明确实喂了），`changes` 为空才有意义。
这条与 #68/#70 是同一族教训的测试版：**绿灯要能回答"它凭什么会红"**。
## 三之补二：第 3 刀已落地（编制说明按自己的小节逐条概括）

**先更正一条我自己写错的"实测"**：先前记「`STRONG_DRAFT` 词表缺『编制说明』」**不成立** ——
词表里本来就有，我当时用 `head -40` 截断输出看漏一行（已在 `a7520cb` 更正）。真实原因是：
25 份说明类附件里 **8 份因"一条公示附件多于 3 个下载名额"根本没下载**，只影响 3 条公示。

更要紧的是另一件事：**13 条公示的说明确实已经进了摘要**（`fed_to_summary=1`），可是提示词只有
一个「附件条文」段落、落库只有一个放条文的字段 —— 说明的内容要么被忽略，要么被当作"规定本身"
概括。这就是"编制说明没针对各个重点要点分析"的机制，不是模型不够努力。

做了什么：

- **附件分角色** `draft` / `explanation`（刻意不收「说明」单字：使用说明 / 填写说明不是对草案的解读）。
- **说明单独一份字数预算**（10,000），不与条文共用 —— 共用时先被喂满的一定是排在前面的条文，
  说明永远只剩个开头，那还不如不给它一个段落。
- **落库按说明自己的小节**（`explanationPoints: {heading, text, quote, source, sourceUrl}`），
  刻意不套"为什么制定 / 依据 / 主要内容 / 征求范围"四个固定框：官方层级写法各异，固定框会逼
  模型往空框里填话，那正是 #55/#56 删掉的那类编造。
- **段落隔离**：条文要点的引用只能在条文段落反查到、说明要点只能在说明段落，串了整条丢弃。
  这不是洁癖 —— 不隔离时，一句出自《编制说明》的话会被标成"摘自官方原文的条文"，
  而读者正是按"规定本身"去读它。
- **覆盖度那句话与改动点同构，但措辞带"约"**：小节识别是行级启发式（`explanationSectionLines`），
  数不出来就说"未检测到分层小标题"，绝不写"共 N 节"假装精确。
- 详情页新增「编制说明要点」一栏（小节标题 + 一句话 + 逐字原文 + 出处）。

测试里钉到的三件事（都有对应的可撤实现）：段落两个方向各一条（条文要点不许借说明、说明要点不许
借条文）、缺引用/缺说明的小节整条不要。另有 3 条 pin。

**这一轮我踩的三个坑，都记下来免得重演**：

1. 说明夹具只有 220 汉字，低于 `MIN_DRAFT_CJK_CHARS = 400` ⇒ "没有说明要点"是**因为压根没喂**，
   断言假绿。补到 417 汉字才作数 —— 与上面那条假绿灯同一族。
2. e2e 里我按 (公示, 附件) 逐次调 `syncAttachmentManifest`，而它会把**本轮清单里没有的行撤下**，
   于是第二次调用把第一条的草案正文删了，表现为整条没喂。改成按公示一次给全清单。
3. 反复用 python heredoc 改文件时，Windows 下按 GBK 解码，**中文锚点全被弄坏**（症状是
   "substring not found"或写进去的字变问号）。此后带中文的补丁一律 `PYTHONUTF8=1` + 片段走文件。

## 四、与最初设计的偏差（记下来，别让下次以为是漏做）

原设计是"现行原文"与"拟改为"**两列**。实现时改成"一列逐字原句"，理由不是省事：
官方对照经常把两者写在同一句里（「第三条修改为：……」「删去第七条第二款」
「增加一条，作为第X条」），要拆成两列就必须让模型改写重述 —— 而那正好毁掉逐字性，
也就毁掉了"这一行能核对"的唯一凭据。所以现在是：
`条款 ｜ 类型 ｜ 一句话说明 ｜ 本站逐字摘录的原句（带出处附件）`。

## 五、还欠的一步：线上真渲染的证据

表格里这条链在测试里是通的（真抓取 → 真反查 → 落库 → 解析），但**线上页面还没真的
渲染出一张改动点表** —— 生产上现有的 52 条修正案，摘要都是在体裁与 changes 字段上线之前
生成的。要拿到那个产物，需要挑 1 条已抽出正文的修正案：清空它的摘要 → 跑一轮 worker
（花一次境外通道调用）→ 抓线上详情页确认表格与覆盖度那行都在。属于生产写操作，等授权。

## 六、下一刀（未开工）

1. **编制说明单独一份结构化摘要**（为什么制定 / 主要依据 / 主要修改内容 / 征求意见范围）。
   修正案那行"影响"只能从这里的明写句子取 —— 这是它存在的理由，不是"再多一栏"。
   ⚠ 更正：先前记的"`STRONG_DRAFT` 缺「编制说明」"**是错的** —— 词表里本来就有，
   我当时用 `head -40` 截断输出看漏一行。实测真正的原因是 3 条公示附件多于 3 个下载名额
   （8 份文件因此 pending），要修的是"名额里给说明留一位"，不是词表。
2. **新案 → 分章逐条**：需要多次调用（成本 / 延迟 / 境外通道暴露面 ×N），
   且今天只对约 9–17 条真有多条结构的条目有效，所以排在后面。
   真要上，触发条件建议就是本刀那行覆盖度：**partial 的比例高到一定量**再上，
   而不是先建好等人来。
第 3 刀的实测底数（生产只读，2026-09-25）：

- 附件名含"编制说明"的 21 行，分布在 13 条公示；含"起草说明"的 4 行；
- 状态分布（说明类合计 25 行）：`ok` 14、`pending` 8（集中在 3 条附件多于名额的公示）、
  `too_large` 2、`unsupported_container` 1 ⇒ **没抽到正文的 11 份里，8 份是名额挤掉的**，
  其余 3 份是文件本身的问题（体积上限与解析失败）；
- 抽出正文的说明**中位 19,207 字**，而单份窗口 8,000 字 ⇒ 说明今天也被截掉约 58%；
- 14 条有已抽出说明的公示里，**13 条的说明确实进过摘要**（`fed_to_summary=1`）——
  可是提示词只有一个「附件条文」段落、落库只有一个 `keyPoints` 放条文，
  于是说明的内容要么被忽略，要么被当成"条文"概括 —— 这正是"编制说明没针对各个重点要点"的机制。

所以第 3 刀要动的是三件事，缺一不可：附件**角色**要分（draft / explanation）、
名额里要给说明留一位、落库形状要能按说明自己的小节逐节承载（不硬套四问框架，那会逼模型填空）。

## 七、有意不做

- **不引入外部知识做"与现行法规对比"**：不可逐字核对，等于把 #55/#56 的地基换掉。
  若将来要做，形态必须是另起一栏、显式标"AI 推断，不在原文里"，且是单独一次决定。
- **不为 126k 字那种超长附件放宽单次调用预算**：先按体裁分流，再看真需要多轮的有多少条。
- **不回填历史页面做版本对比**（迭代 3 撤销的那件事）：与体裁无关，别混进来。
