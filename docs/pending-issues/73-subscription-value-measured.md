# issue #73：订阅闭环在今天的生产数据上到底会给多少东西（一个数，不是感觉）

延续 #68/#70/#71/#72 那条线，这次量的是迭代 4 的闭环："四刀都上线了"是真的，
但**它今天能给一个订阅者发多少东西**没被算过。#70 已经测到 `reminder_sends` 与
`notice_notifications` 各 0 行 —— 那是"没有可发的收件人"，不是"没有可发的内容"，
两者要分开，否则会把需求问题误判成 bug（或反过来）。

工具：`scripts/audit-subscription-value.mjs`（只读，不写库、不发信）。规则判定**复用发信任务
同一份** `matchesSubscriptionRules()`，条目集合也按库列 `status='open'` 算（展示层的
`effectiveStatus` 不是发信口径）—— 另写一份判据就等于在量一个生产上不存在的实现，
这个理由与 #67 导出 `draftSourcesForSummary()` 给脚本用是同一个。

## 这三行说明什么

1. **一周的新公示只有 5 条**（全站、订全部的天花板）。所以"新公示通知"这个功能当前的产出上限
   是每周 5 条以内 —— 它是为"别漏"存在的，不是为"信息量大"存在的。想判断值不值，看这个数，
   别看 story 有没有实现。
2. **站长现在这条规则（关键词"数据"）本周会收到 0 封新公示通知** —— 本周新增的 5 条里没有一条
   含"数据"。但同一个规则**会带来 5 封截止提醒**（命中的 9 条 open 里有 5 条在 7 天内截止）。
   也就是说：如果只做一件事来提升这套闭环的可感知度，是**恢复订阅**，不是改通知逻辑 ——
   提醒侧本来就有东西可发，卡点只在"可发订阅者 = 0"。
3. 两个数都还是 0（`reminder_sends` / `notice_notifications`）的唯一原因是收件人为 0，
   与 #70 的结论一致；这条把那件事从"推测"变成"算过"。

## 待授权的那一步（合并进 task #44）

要真把这两条路径验成"有产物"，最小动作是把站长自己的订阅恢复成可发（清 `unsubscribed_at`），
然后跑一轮 worker：**按上面的数，应当出现 5 条左右 `reminder_sends` 行、0 条新公示通知**。
这既是生产数据写入也是对外发信（收件人是站长本人邮箱），所以要打字授权。
做完的判据是明确的：`reminder_sends` 从 0 变成非 0，且邮件真的在 QQ 邮箱里能看到。
