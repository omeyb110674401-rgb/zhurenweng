# issue #65：没有「按来源」这一维，源悄悄停止交付也看不见（迭代 5 第 4 刀）

对应提交：（第 4 刀）

## 一、这一刀解决什么

两件此前无处可查的事：

1. **一个源可以天天抓取成功、看板全绿，却连续几周一条新的都不送。**
   issue #58 把「判红」的依据改成 `consecutive_failures`（连续失败轮数），那挡的是
   「报错型」故障。另一类故障它看不见：请求都成功、页面都在、就是没有新条目
   （源站改版、栏目换址、列表选择器失效）。对只有一个运维人的站点，这类退化是
   最可能长期无人发现的一种。
2. 统计页（issue #11 起）只有机关、月份、公示期、点击四个维度，**没有按来源的表**；
   首页也没有 `?source=`。想知道「交通运输部这个栏目到底送了多少条、最近一次是什么时候」
   只能进数据库跑 SQL。

## 二、做了什么

- 仓储层新增 `listNoticeSourceFacets()`：按 `notices.source_id` 聚合出
  **收录量 / 未截止量 / 最近一次新收录（`max(first_seen_at)`）**，并把登记表
  （`sources`）里的名字与「是否还在登记表里」一并带出。
- 首页：来源下拉（`?source=`），与筛选条其余维度同样纯 URL 驱动；当前值不在选项里时
  补成选项并选中（issue #39 的同一处理）。
- 统计页新增「各来源收录量」表，两格数字都是钻取链接：
  收录量 → `/?source=…`，未截止 → `/?source=…&open=1`。
- 子 feed 也吃 `?source=`（沿用 #63 那份参数口径）。

## 三、几个决定的理由

**「最近新收录」是这张表存在的理由**。判据用 `first_seen_at`（#60 第 3 刀加的列，
建行时写入、不随每日抓取覆盖），不是 `fetched_at` —— 后者天天被覆盖，用它这一列
会永远显示"今天"，正好把要揭穿的故障盖住。这与 #62 的 `?since=` 是同一个判据。

**零收录的源也要在表上**。聚合查询只会给出有条目的源，所以这里把登记表的源并进来
（count 0）。被聚合结果"自然挤掉"的正是最需要看见的那一行。

**「未截止」那一格与 `?open=1` 共用同一份 SQL 判据（`openCondition()`）**。
issue #36 的不变式是「点进去的条数 = 表格上的数字」；如果表上按库列 `status` 数、
点进去按展示口径筛（#43 的那件事），两个数就会差在「刚过期还没被抓取改口」的条目上 ——
这种偏差平时看不见，凑巧过期几条就对不上。为此把判据抽成一个函数，WHERE 与 CASE 都用它。

**条目引用了登记表外的源时照列，并标注「未在源登记表」**。这是 #58 清掉 `govcn`
适配器死行之后留下的形状：条目还在、源没了。静默归并或漏行会让「各行之和 = 收录总数」
对不上而没人发现（issue #46 的同一件事），所以宁可多标一列、多写一行差额提示。

**`?source=` 不做值白名单**。`category` 白名单是因为词表写死在代码里，页面与它不可能
不一致；来源清单在数据库里、每天在变，白名单会让"新注册的源"要先改代码才能筛。
处理方式与 `agency` 一致：不认识的 ID 筛出 0 条，并把该值回显在下拉里（控件不撒谎）。

**「最近新收录」按站点日历日显示，不是截时间戳前 10 位**。存的是 UTC 时间戳，
北京时间 00:00–08:00 那一段直接截断会少算一天（issue #40 的同一件事）。
表格里的原文 `2026-09-22T11:25:00.000Z` 也不是给人读的，走 `siteDateIso` 折成 `2026-09-22`。

## 四、测试与自证

- `tests/e2e/source-facets.test.mjs`（16 例）：
  - 仓储层（6 例，直调函数 ⇒ pins 撤得动）：零收录的源在结果里、未截止格按展示口径、
    登记表外的源标注且名字退回 ID、**「最近新收录」取的是该源最新那条（`max`，
    三条种子分别 -2 / -20 / -40 天）**、各行之和 = 条目总数、`sourceId` 与其余维度
    叠加且 count 与 list 同口径；
  - 统计页（5 例，走真实 HTTP）：**每一格数字点开后页面真实渲染的条数与之相等**、
    各行之和 = 页首收录总数、日期格是站点日历日而不是裸时间戳、差额提示点名未登记的源；
  - 首页与 feed（5 例）：下拉带条数、摘要显示名字不是 ID、vanished 源的选中态、
    与其它维度共存、子 feed 与首页同集合。
- `tests/unit/home-query.test.mjs`（+3 例）：`source` 是筛选维度、口径说明里的名字/ID 回落、
  子 feed 地址带上 source。
- `scripts/check-test-pins.mjs`：74 → 83 条。**首跑 81/83，两条各自暴露一个问题**：
  1. #62 那条「只看未截止只看库里状态」的 `from` 片段找不到 —— 本刀把判据抽成
     `openCondition()` 后缩进变了（10 空格 → 6 空格）。**抽出共用函数是好事，
     但它会静默作废锚在旧位置上的 pin**；片段跟着挪了。
  2. 「不取最近收录时间」撤掉实现后测试仍然绿 —— 因为**没有任何一条断言检查过
     一个非 NULL 的 `last_first_seen_at`**（丙源那行断言的恰好是 null，撤掉 `max()`
     后它还是 null，假绿）。补了"甲源三条不同收录时间，取最新那条"的断言之后才红。
     这与 #63 那条假绿是同一个形状：pins 报红的前提是"测试真的看过这个值"。
- 一处**测试环境造成的形状限制**（记在这里，免得后人以为是漏测）：
  SQLite 侧 `notices.source_id` 带外键（PG 侧没有），所以"条目挂着不存在的源"在本地
  无法用正常写入造出来。测试的做法是先登记、再入库，然后**关掉外键删掉登记行** ——
  复刻 #58 现场。这不是绕开断言，但它是绕开了 SQLite 的约束，值得写明。

## 五、上线后值得看的一眼

部署后打开统计页这张表，按「最近新收录」看一遍：**任何一行停在两周以前，就是一个
抓取成功但不再交付的源**，该去核对该源的选择器。这是本刀的实际用途，也是它唯一的
验收标准（代码全绿不代表那批源真的健康）。
