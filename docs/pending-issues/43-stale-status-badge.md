# 状态列每日一轮，过期条目在下一轮抓取前仍显示「征求意见中」

## 审计结论（2026-09-21）

| 检查项 | 结论 |
| --- | --- |
| `/admin` 鉴权与只读性 | 无缺陷 —— 未授权 GET 实测 401 引导页；六个路由全部过守卫（页面 / 补录 / 复核 / 源开关 / 登录 / 登出）；写操作 POST-only，GET 得 405 |
| `/admin` 的 HTML 拼接转义 | 无缺陷 —— 手写 HTML（`admin-html.ts`）的每个动态值都过 `escapeHtml`，含抓取错误信息与源名这类任意内容 |
| `/subscribe` 表单边界校验 | 无缺陷 —— 邮箱长度 + 形状、关键词数量/长度上限、领域白名单、至少一条规则；退订后再订阅会把 `unsubscribed_at` 清掉并重签 token（不会出现「确认了却永远收不到」） |
| `feed.xml` 转义与排序 | 无缺陷 —— `escapeXml` 覆盖 channel 与 item 全部字段（`&` 优先转义），按发布日期倒序、上限 200、`guid isPermaLink=false`、`atom:link rel=self`、`no-store` |
| **状态徽标的新鲜度** | **缺陷**（见下） |

## 缺陷：页面声称一个已关闭的征集还能提意见

`notices.status` 是**抓取时**推导的，而抓取每日一轮（生产 `WORKER_INTERVAL_MS=86400000`，
实测上一轮 14:05 北京时间）。于是北京时间 00:00 到下一轮抓取之间（约 **14 小时**），
刚过截止的条目在库里仍是 `open`，页面上同时出现两个错误信号：

1. 徽标写「征求意见中」；
2. 倒计时因为 `daysUntil < 0` **静默消失** —— 不是显示「已截止」，是什么都不显示。

读者看到的是「还能提意见、而且没有截止提醒」，而旁边的按钮正在邀请他
「去官方渠道提意见」—— 提交到已关闭的征集。生产实测（2026-09-21）：
**今天到期的 6 条**，今晚 00:00 起就会这样挂到明天下午下一轮抓取为止；此后每天
都有 1–6 条落进这个窗口（09-23 有 5 条、09-26 有 6 条）。

## 修复

新增 `src/lib/notice-status.ts` 的 `effectiveStatus(notice, now)` —— **只复核需要复核的
那一档**：

- `resulted`（已出结果）以库内为准：那是源站标注的结果状态，日期推不出来；
- `closed` 同理：源站可能提前结束征集，比日期更权威；
- 只有 `open` 按当前日期再判一次：截止日已过 → 已截止（按北京日历日，与
  `daysUntil` 同口径 —— issue #40 已把日历口径钉死在东八区）。

接线三处**展示**口径：列表徽标（`notice-item.tsx`，首页与搜索结果共用）、
详情页徽标、分享摘要（`generateMetadata` 的 description）与结构化数据的
`creativeWorkStatus`（`buildNoticeJsonLd` 新增可选 `status` 覆盖）。摘要与结构化数据
一并改口是刻意的：分享链接会被转发出去、结构化数据是给机器读的声明，**没人会回来
纠正一个已经发出去的「征求意见中」**。

**不改聚合与排序**（首页把 `open` 排在前面、统计页不做状态分布、提醒任务只认 d7/d3）：
那些是抓取口径，动它们要先定产品口径（让抓取更频繁？还是让查询层推导？）—— 已记录为
后续议题。展示层改口不会与它们冲突：首页排序里「即将截止」本来就在最前。

## 验收

- 单元（138，新增 7）：`notice-status.test.mjs` 六项 —— 已过期改口、**当天不算过期**、
  未来不变、取不到截止日期不擅自改口、`closed`/`resulted` 以库内为准、北京日历日边界
  （北京 09-21 00:30 时截止 09-20 的条目已过期 / 北京 09-20 23:59 仍算当天）；
  `notice-jsonld.test.mjs` 新增「状态可覆盖」一项（并保留不传时的向后兼容）；
- E2E（179，新增 2）：`status-freshness.test.mjs` —— 真实抓取一轮后把测试进程时钟
  拨过最快到期那条的截止日（node:test mock.timers，应用与测试同进程）：该条徽标必须
  当场变「已截止」、倒计时不再静默消失，**最远到期的那条不受影响**；详情页徽标、
  JSON-LD 的 `creativeWorkStatus`、meta 摘要三处必须同为「已截止」。
  两次请求之间不重跑 worker，所以库内 status 不可能变 —— 翻转只可能来自展示层复核；
- **红检**：把三处接线退回库内状态（`effectiveStatus(notice, now)` → `notice.status`）→
  e2e 当场变红（断言「过了截止日就必须改口，不能沿用库内状态」）；
- 本地全量：单元 138 + E2E 179 全绿，typecheck / lint 干净；
- 线上核验（部署后）：**全量不变式** —— 逐页抓取首页 4 页共 178 条，比对每条徽标与
  「截止日 vs 北京今天」，**0 条矛盾**（既没有过度翻转，也没有该改口没改口的）；
  今天到期的 6 条今晚 00:00 起会当场改口（此前要等明天下午的抓取）；
  抽查一条今天到期的：列表徽标 / 详情徽标 / 倒计时（今天截止）/ JSON-LD / 分享摘要
  五处口径一致；容器内用注入时钟核对部署后的规则两侧 —— 今天截止 @北京 14:00 → open、
  @23:59 → open、@次日 00:30 → closed，未来截止 → open，已出结果 + 已过期 → resulted，
  源站提前结束 → closed；首页 / 统计页 / feed / sitemap / 第二页 全部 200。

## 未做（有意）

- **不改库内 `status` 列**：它是抓取口径的缓存，改它要连带动 upsert、列表排序与提醒
  任务；展示层复核已解决读者看到的问题；
- **不给按钮加「已截止」文案**：按钮仍指向官方原文（那是官方页面的正确出口），
  徽标已经说明状态 —— 改文案属于产品口径，等聚合口径一起定；
- **不改抓取频率**：把窗口从 14 小时缩短到 1 小时需要每小时一轮抓取，对十个政府站点
  是不礼貌的负载；展示层复核的收益/代价比明显更好。
