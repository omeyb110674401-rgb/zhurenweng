## 一、检索后端还能不能搜到今天存在的条目

`scripts/audit-search-index.mjs`（新增，只读）。判据是**自证式抽样**：按 id 排序每 N 条取一条，
拿它自己标题里的特征片段（优先《》内的法规/标准名，否则前 10 字）去搜，看它自己在不在前 20 名里。
刻意不用整条标题 —— 标题里全是机关名与「征求意见」这类共有词，命中别人也算对，测不出漂移。
漏网还分两类，因为处置不同：`total=0`（多半根本没进索引）与"有命中但排不进前 20"（排序/分词）。

生产实测（每 6 条取 1，共 32 条样本，provider=meilisearch）：

```
[audit-search] provider=meilisearch 库内 192 条，抽样 32 条（每 6 条取 1，前 20 名内算命中）
[audit-search] 32/32 条都能被搜到
```

**没抓到问题** —— 这一条是有价值的：#67 刚把 49 条摘要重写过，索引同步是钩子 + 每轮全量重建两层，
如果钩子静默失败，表现正是"页面都正常、搜索少结果"。现在它被测过，而不是被相信过。
退出码在非零漏网时为 1，将来要接 cron 告警可以直接用（与 #71 同一族）。

## 二、出站点击的两套口径有没有已经漂移

FOLLOWUPS 的 #52 那行记着一个已知风险：`recordOutboundClick` 写两处 ——
`notices.outbound_clicks`（详情页那行「出站提意点击：N 次」用）与 `outbound_click_daily`
（统计页 Top 榜与按日趋势用）。第一条成功、第二条失败就会漂移，而**两处都在被读者当数字读**。
当时判断"包事务做不到"（实测 drizzle 的 better-sqlite3 事务不接受 async 回调）而保留 ——
但保留的前提是"漂移没在发生"，那是推断，不是证据。

| 条目列相加 | 日表相加 | 差额 | 日表行数 |

| 113 | 113 | **0** | 96 |

## 三、顺手记一条操作法：跑只读探针不必重建镜像

`docker compose run` 用的是**镜像里的代码**（#67 为此踩过：同步了脚本，跑的还是旧版）。
但只读探针不值得为它 build 一次镜像。这次用的是把宿主机的文件挂进临时容器：

```bash
docker compose run --rm \
  -v /opt/zhurenweng/scripts/audit-search-index.mjs:/app/scripts/audit-search-index.mjs:ro \
  worker node scripts/audit-search-index.mjs --stride 6
```

`worker` 镜像的 `WORKDIR=/app`，脚本 import 的 `../src/**` 都在镜像里，所以挂载单文件即可；
`:ro` 保证探针改不到容器里的代码，跑完容器就消失，**不触碰线上镜像与常驻服务**。
（改的是真正要被 worker 长期执行的代码时，仍然要 `build` + `up -d`，见 `deploy/README.md`。）
