## 四、第 5 步的输入预算（为什么不是"全文塞进去"）

`worker/jobs/summarize-notices.ts` 的 `draftSourcesForSummary()`：

- 条数：每条公示最多 3 份（`MAX_FILES_PER_NOTICE`），取字数降序（字数多更可能是草案本文）；
- 每份 8,000 字，且**按结构感知截取**（`excerptForPrompt` 优先保留「第 X 条」锚点窗口 ——
  草案开头的目录与起草说明里没有条文，简单取前 N 字等于花钱买废话）；
- 全部合计 ≤ 12,000 个汉字；**装不下就整份不送**，不把最后一份切一半
  （半截条文会让模型把截断处当成规定本身）；
- 字数门槛 400（`MIN_DRAFT_CJK_CHARS`）：低于它的按 `no_draft_text` 处理，不喂。

仍然是一次 LLM 调用 —— 拆成两次会让最坏情况的单条耗时从 4×300s 变成 8×300s，
而 #55 实测境外通道单次 87.6s。

## 五、第 6 步：出处由程序反查，不由模型自报

风险从头到尾只有一个名字：**模型把公告壳里没有的东西说成草案条文**（#56 正是因此删掉了
「关键条款」）。防线不是提示词措辞 —— 模型不遵守时页面上看不出来。

`buildQuotedSummary(summary, quotes, draftSources)` 在落库前逐条核对：

1. 拿这条要点的引用，在**本轮真正喂进去的那几份条文**里做逐字比对；
2. 比对用"去空白指纹"（PDF/DOCX 抽取自带换行与缩进，模型常压成一行，按原样比对会把
   真的逐字引用判成对不上）；
3. 引用短于 8 个字符不算出处 —— 「第三条」这种片段在任何公文里都能蒙中；
4. **核对不上就丢弃这一条要点**（其余保留）。于是「页面上出现了条文要点」的必要条件
   变成"附件正文确实进了提示词"，与档位叫什么、模型听不听话都无关。

出处是**程序算**出来的（哪份条文的指纹含住了这条引用），不是模型报的：它会把两份附件的
内容混标到其中一份上，而读者从页面上看不出这种错配。

详情页摘要卡底部改为四分支（`draftAvailability`，只看库里事实、不看档位名）：
读到了并用于本页要点 / 读到了但本页未用 / 有附件但读不到（说清几份） / 没有随文附件。
「抽取表里没行」**不等于**"没有随文附件"（可能是抽取还没跑到）—— 分不清就报未探测，
回到改动前的通用文案。
