# sitemap 的 lastmod 写成了我们的抓取时间：178 条全部声称「今天改过」

## 审计结论（2026-09-21）

| 检查项 | 结论 |
| --- | --- |
| **sitemap 的 `lastModified` 口径** | **缺陷**（见下） |
| 404 与错误页 | 无缺陷 —— 边界探针（2000 字符查询 / 超大页码 / 5000 字符领域值与 token / 64 位假 id / 不存在的路径）全部 200 或 404，**没有一个触发 500**；404 页是中文说明 + 回站入口 |
| 统计页月度趋势的钻取入口 | **缺功能而非缺陷** —— 趋势表单元格与行合计都是纯文本；但「按机关」那一维在首页筛选中**已有**对应口径（issue #36 的 `lead=1`），而「按月份」还没有（首页筛选表达不了「某月」）—— 加钻取必须先定 URL 口径，仍留后续 |

## 缺陷：写给爬虫的「最后修改时间」是假的

`sitemap.xml` 里每个条目页的 `lastModified` 用的是 `notice.fetchedAt` —— **我们抓取的
时间**。抓取每日一轮，于是线上实测：

```
178 条 <lastmod>，日期分布：[('2026-09-21', 178)]      ← 全部是当天
```

而绝大多数页面的内容根本没变（官方文档发布后是静态的）。这不是「不够精确」，是**事实
错误**：搜索侧对持续失真的 `lastmod` 会直接降低信任（Google 文档明说会忽略不可靠的
lastmod），于是「这一条真的更新了，值得重抓」这个信号也一起失效 —— 我们白白丢掉了
一个抓取调度工具。

## 修复

`lastModified` 取**内容时间**：

- 条目页 → `publishedAt ?? fetchedAt`（文档发布即定型，这就是「这一页什么时候变成
  现在这样」的真实答案；发布日缺失时退回抓取时间，不写空值 —— 生产实测缺失 0 条）；
- 列表页与统计页 → **刻意不写** `lastModified`：它们的「上次变更时间」我们并没有记录，
  省略是合法的，写错会污染信号。

## 验收

- E2E（180，新增 1，`category-filter.test.mjs`）：① 逐条比对 —— sitemap 里每个条目页的
  `lastmod` 必须**等于站点上显示的发布日期**（两处口径一致，站点地址从 sitemap 自身
  推导，不写死）；② 反向断言 —— 只要有一条 `lastmod` 不是今天，就证明写进去的不是
  抓取时间（全部都是今天 = 修复前的老行为）；
- **红检**：把 `lastModified` 改回 `notice.fetchedAt` → 新断言当场变红
  （「lastmod 应等于站点上显示的发布日期」）；
- 本地全量：单元 138 + E2E 180 全绿，typecheck / lint 干净；
- 线上核验（部署后）：sitemap 仍 180 条、178 条带 lastmod（首页 / 统计页不带）；
  **`lastmod` 恰好等于今天（抓取日）的条数从 178 变成 0**；日期分布覆盖
  2016-09 → 2026-09（与库内发布月份一致，其中最早的是教育部历史归档）；
  **全量不变式：逐页抓 178 条，比对 sitemap 的 lastmod 与页面上的发布日期，0 条不一致**；
  首页 / 统计页 / feed / robots / sitemap 全部 200。

## 未做（有意）

- **不新增「内容变更时间」字段**：严格说 lastmod 应该是「内容最后一次变化的时间」，
  而我们会补抓正文（issue #24 那次补了 7 条空正文）—— 要精确表达需要给 notices 加一列
  内容变更时间（迁移 + upsert 比较 + 测试）。当前口径（发布日期）对 99% 的条目就是真值，
  且**不会说假话**（只说「旧」不说「新」）；记为后续；
- **不补 `error.tsx`**：没有触发路径（探针全 200/404），加了也无法线上核验；等真的
  出现 500（例如库不可用）再加更合适 —— 那时才知道要给它什么文案；
- **不给统计页趋势表加月份钻取**：要先定 URL 口径（`?month=YYYY-MM`？区间？），
  且必须保证「点进去的条数 = 表格数字」（issue #36 定的不变式），留作独立议题。
