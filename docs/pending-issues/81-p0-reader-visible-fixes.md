## 一、#79：体裁词表与改动计数「同源」这件事，以前只是注释

`79-amendment-genre-false-positive.md` 记的是现象（44% 的修正案会渲染出一个空的
「改动点」栏）与根因（两份词表不一致）。这一节记**执行**，三处一起改：

### 1. 词表拆成两组，关系由单测钉住（`src/lib/notice-genre.ts`）

```ts
export const CHANGE_TEXT_MARKERS = ['修改为', '删去', '增加一条'] as const;   // 既判体裁、也计数
export const GENRE_ONLY_TEXT_MARKERS = ['原条款'] as const;                  // 只判体裁、不计数
export const AMENDMENT_TEXT_MARKERS: readonly string[] = [
  ...CHANGE_TEXT_MARKERS, ...GENRE_ONLY_TEXT_MARKERS,
];
```

为什么不是继续用一份清单：#76 那两句注释（"判体裁和算覆盖度必须认同一批词，否则会出现
判成修正案但覆盖度算出 0 处改动这种自相矛盾的页面"）**本身是对的**，错在没有任何东西
保证它成立 —— 两份表各自被测试钉住，**它们之间的关系没人钉**，于是加词的人只想着让判定更准。
现在关系是显式的：想进 `CHANGE_TEXT_MARKERS` 的词必须真的数得到；只想判体裁的词得进
`GENRE_ONLY_TEXT_MARKERS` 并写明理由。

### 2. 「现行」移出（这是那 22 条的来源）

判据不是"我觉得它不准"，是**语料本身**：全新标准的编制说明里本来就会写"现行标准 /
现行法律"。移出后那 22 条按标题与新案措辞重判（走向见第二节）。

`原条款` 留下但只判体裁：它预设了"有一份现行文本"，本身不是一处可数的改动 ——
数它只会数出一个假的分母。于是"判成修正案但一处改动都数不出来"这个状态**仍然可能发生**，
它由渲染层兜底，而不是靠往计数表里塞词硬凑一个数字（那是用一个错数换一个空栏）。

### 3. 一行改动点都没有时，整节不渲染（`src/app/_lib/summary-view.tsx`）

原来的条件是 `changes.length > 0 || changeMarkers !== null` —— 只要摘要里带过一份覆盖度
（哪怕分母是 0）就渲染，于是长出一个标题写着「改动点」、note 却说"没检测到改动"的空栏。
现在与「编制说明要点」（`explanationPoints` 为空即整节不出现）同构：**一行都没有就不出现，
连标题都不出现**。

空栏传达的不是"改动点是空的"，而是"这一栏没东西可看" —— 后者不该占一个标题。
而"这一条还能不能提意见、本站读没读到条文"这两件事，摘要卡底部的 `draftAvailability`
本来就有一栏在说，不靠这个空标题兜底。

### 4. 文案不再替判据编一个来源（`src/lib/amendment-coverage.ts`）

旧文案硬编码「（按标题判为修正案）」，而这 22 条的判据是**附件正文**。现在
`changeCoverageVerdict(listed, markers, genreBasis?)` 接收真实的判定依据（详情页传
`notice.genreBasis`）并照抄出来；没传就只说不给数字：

> 附件正文里没有数到成文的修改表述，这一栏给不出「共几处」；这条判为修正案的依据是：附件正文含对照措辞「原条款」

## 二、存量怎么改过来：回填被它自己的守卫挡住了 ⇒ 加了 `--force`

这是本轮**只有拿生产数据量过才会发现**的一件事。`scripts/tag-notice-genres.mjs`
（#76 写的存量回填）复用 `genreDecisionWins`：**弱的证据不许覆盖强的**。
收窄词表之后，那 22 条重算出来一律是"标题级证据"（rank 1），比存着的
`attachment_text`（rank 3）弱 ⇒ 全走 `skipped`，**一条都改不动**。

也就是说：只改词表 + 只补渲染，那 5 条本该是新案的条目会继续挂着「修正案」角标、
继续用修正案模板 —— 页面不再自相矛盾，但体裁仍然是错的。所以
`backfillNoticeGenres` 增加 `force`（脚本对应 `--force`）：它不改判据，只承认
**强弱是同一套词表内部的相对关系，词表本身换了，旧的"强证据"就只是一条过期结论**。
`force` 仍尊重"算出来与存量逐字相同就不写"，所以重复跑是幂等的（有测试钉住）。

## 三、首页头屏不该是已截止

### 根因

聚合排序的第一档用的是**库内 `status` 列**：`case when status = 'open' then 0 else 1 end`。
而那一列是**抓取时**推导的缓存，抓取每日一轮 —— 昨天到期的那批在下一轮抓取改口之前仍是
`open`，于是首页头屏排满了页面自己标着「已截止」的条目（生产实测：头屏 9 条，整页 50 条里 18 条）。
一个以北极为"出站提意点击数"的站，第一屏不能是已经提不了意见的东西。

这一条**不是 #62 引入的回归**：那第一档自 09-12 就是 `status`（`?sort=` 四档只是复用了它），
属于老债 —— 我第一反应记成回归，查完提交历史后更正了。

### 修法：第一档改用展示口径，且必须每次查询现算

`stillOpen()`（原名 `openCondition()`）本来就是「这一条还能不能提意见」的 SQL 判据，
`?open=1` 的 WHERE 与统计页「未截止」列都用它。现在它是**第三个**调用方：

```ts
function aggregationOrder(): SQL[] {
  return [
    sql`case when ${stillOpen()} then 0 else 1 end`,
    sql`case when ${notices.deadlineAt} is null then 1 else 0 end`,
    asc(notices.deadlineAt), desc(notices.fetchedAt), asc(notices.id),
  ];
}
```

三处从此同源：排序看到的"还能提"，就是徽标和筛选器说的"还能提"。

**`ORDERS` 从"数组常量"改成"构造函数"**，因为这一档里的"今天"来自
`siteDateIso(new Date())`，而 web 进程长期驻留 —— 写成模块级常量等于把"今天"冻结在
进程启动那一刻，午夜过后新过期的条目仍按未截止排序，直到下次重启。这个坑与
`openCondition()` 当初写成函数是同一个理由，而**排序这一档更容易被顺手提成常量**
（原来它就是常量），所以理由写在了代码里。

### 连带：5 处测试期望改了 —— 它们此前把缺陷编码成了期望

`discovery-repo`、`discovery-controls` 里丁（库里写 `open`、截止日 −1 天）**原本排在第一位**，
而同一份测试的用例名写着「不带参数 = 原倒计时序（**未截止优先** → 截止升序）」。
名字是对的，断言与实现都在按库列判 —— 一个"说 A 测 B"的期望。
现在丁沉底，期望改成 `[B, A, E, C, D]`（未截止的按截止升序在前、已截止的沉底）。

### 自证框架（`check-test-pins.mjs`）本轮抓到 3 处，其中 2 处是我改出来的

跑全套（不是只看新增门）的价值在这里：

1. **「列表排序参数被忽略」** —— 我把 `ORDERS` 改成构造函数后，片段的 `from`

3. **「体裁不门控产品形状」—— 这条在我改之前就已经是"撤了也不红"**：它的可观测点依赖
   `现行` 被 stub 回响（新案夹具的正文里只有「现行」这一处"像改动"的话），
   而本轮把 `现行` 从词表里去掉、并让 stub 改认**可计数**的那份词表（`CHANGE_TEXT_MARKERS`）

   修法不是删 pin，而是补夹具：新增一条**打包清单**（`genre=package_plan`，
   标题「关于征求《某某法》等2项法律草案（修正草案征求意见稿）意见的公告」）
   并挂一份真正的"修订对照"正文 —— 模型完全有理由对它吐出一张改动点表，
   而体裁门必须把它清掉。另外顺手补了这条门的**另一半**（分母也不给非修正案算），
   于是 pin 从 1 条变 2 条。

   为什么不能用新案夹具承担这件事：新案的说明里写"与现行做法相比删去了…"看着够真，
   但 `changes` 的逐字反查**只认草案那一侧的段落**（说明的话不许当"规定本身"落库），
   所以新案无论如何都产不出改动点 —— 这一条我踩过一次才想明白，写在夹具注释里了。

另：`check-test-pins.mjs` 这个脚本**仍然没有调用者**（`package.json` 里 0 个入口），
