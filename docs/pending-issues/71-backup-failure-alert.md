# issue #71：备份失败原本"只有日志知道"，而没有人读那个日志

父 issue：`59-iteration-baseline.md`（每日备份 + 恢复校验）、`68-backup-cron-never-fired.md`
（那条 cron 从未触发）。#68 之后我把"有没有真实产出"这把尺子继续往下量，量到**失败路径**上：
`daily-backup.sh` 失败时非零退出，cron 把输出写进 `/var/log/zhurenweng-backup.log` —— 然后呢？
没有然后。**没有人在读那个文件**。

## 一、问题：一个只在"没人看"时才有用的告警面

备份脚本本身做得比多数项目认真（先写 `.part` 再改名、归档小于 10KB 直接判失败、
每次重建临时库真恢复、6 项计数对不上就非零退出）。但它所有的失败表达都只有一种形式：
**退出码 + stdout**。而 cron 的 stdout 落进一个没人看的日志文件。

这与 #68 是同一族缺陷，只是更隐蔽：#68 是"该跑没跑"，看得见的证据（产物）缺失，
至少理论上能查；这一条是"跑了但失败了"，**没有任何东西会主动找到你**。
备份恰好属于最不能静默失败的东西 —— 它的全部价值在于某天要恢复时它得存在。

## 二、修法：复用 worker 已有的告警出口，不新造一套

`scripts/alert-backup-failure.mjs` 只做一件事：调 `sendTaskFailureAlert({ jobName:
'daily-backup', sourceId: null, error: <原因> })`。为什么复用（`src/lib/alerts.ts`）而不是
在 bash 里自己发邮件：

- **未配置 ALERT_EMAIL 就整体跳过** —— 开发机 / 测试环境不会莫名其妙发信；
- **按 日历日 × 任务名 × 源 去重** —— 备份连续坏三天只发一封，不会把站长邮箱刷爆，
  而且去重落在 `alert_sends` 表里，重启进程也还生效；
- **自身绝不抛** —— 告警路径坏掉不能把备份本身搞挂。

`sourceId` 传 null：备份不是某个抓取源的故障。塞一个假 ID 会让邮件里出现
「源：postgres-db（未在源登记表）」这种误导话。

脚本侧的 `deploy/daily-backup.sh` 加了两样东西：

1. `STEP` 阶段名（导出 / 恢复校验 / 保留清理 / 完成）——只给退出码的话，收信的人还得猜
   是导出挂了还是校验没对上；
2. **一条**退出陷阱：`trap 'rc=$?; if [ "$rc" -ne 0 ]; then alert_failure "$rc"; fi; exit "$rc"' EXIT`。

这里有一段值得记的弯路。**我最初写的是两条陷阱**：`ERR`（抓命令失败，能带行号）+ `EXIT`
（抓脚本自己 `exit 1` 的那两处），再配一个 `ALERTED` 守卫防止两条各发一封。听着周到，
但自证门（`check-test-pins.mjs`）跑出来是：

> 备份失败不再发信（ERR trap 撤掉 ⇒ 坏了只有日志知道）—— **撤掉实现后测试仍然通过**

原因很干脆：`set -e` 下命令失败也会走到 `EXIT`，两条陷阱能做的事完全一样，`ERR` 唯一多出来的
只有一个行号。**为了行号养一条重复的告警路径 + 一个防它自己发两封的守卫，不值。**
于是删掉 `ERR` 与 `ALERTED`，只留一条 `EXIT` —— "恰好一封"从"需要守卫维持"变成"结构上就成立"。
要查具体哪行失败，看 cron 日志（邮件里给阶段与退出码，够定位到步）。

这也是这个门第 N 次发挥作用的例子：它不只防"断言没钉住实现"，还防"实现了多余的机制"。

告警脚本**永远零退出**：它是"报错时的第二只手"，它自己的成败不能把备份的原始退出码盖掉，
否则日志里看到的是"告警脚本挂了"，而真正该知道的"备份没做成"被换掉了。

## 三、测了什么（这些性质在 bash 里，读代码看不出来）

`tests/e2e/backup-failure-alert.test.mjs`，7 条（"恰好一封""阶段名""退出码保留"这些性质
只存在于 bash 与 trap 里，读代码看不出来，所以测试**原样跑仓库那份脚本**而不是复刻逻辑）：

- 造一个假的 `docker` 放进 PATH，记录每次调用并按需让某一步失败，**原样跑仓库里那份脚本**：
  导出失败 ⇒ 退出码 7 被保留、告警**恰好一封**、内容带 `阶段=导出`；
  校验对不上（脚本自己 `exit 1`）⇒ 仍然恰好一封、带 `阶段=恢复校验` 与"恢复后 4 条"；
  全程顺利 ⇒ 一封都不发（天天发"备份成功"等于没有信号）。
- 直接跑告警脚本本体（stub mailer + 临时 SQLite）：真写出一封信且内容能认出是备份；
  **共用同一个库**跑第二次 ⇒ 被当日去重挡掉；`MAILER_STUB_FAILURES=always` ⇒ 仍零退出；
  没配 ALERT_EMAIL ⇒ 安静跳过。
- 自证门新增 2 条 pin：撤掉那条退出陷阱 ⇒ 失败用例收不到告警；把 `jobName` 改成
  `crawl-notices` ⇒ 邮件里认不出这是备份（两条都实测过红）。pins 89 → **91**。
  原本还写了"撤 ERR trap""撤 ALERTED 守卫"两条 pin，实现被门判成多余之后就一起删了 ——
  **留下测不到行为保护的 pin，比没有 pin 更糟**。

写这个测试时踩到自己两个坑，都记下来免得再犯：JS 模板字符串里写 shell 注释**不能带反引号**
（会把模板提前结束）；用 python 批量改 JS 文件时 `'\\n'` 会变成真的换行符 —— 这类改写要么用
`Edit` 要么把 python 串写成 raw。两次都是测试自己假绿/加载失败，靠"跑一遍看红不红"抓出来的。

## 四、部署与未做

- 生效需要把两个文件同步到服务器（`deploy/daily-backup.sh`、`scripts/alert-backup-failure.mjs`）。
  cron 跑的是**宿主机上那份脚本**，所以同步即生效，不需要重建镜像；但脚本里调的
  `docker compose run --rm worker` 用的是**镜像里的代码** ⇒ 告警脚本必须进镜像，
  也就是仍要走一次 `docker compose build worker`（#67 记过这条"同步 ≠ 部署"）。
  **属生产变更，等授权。**
- 未做：**成功心跳**。现在"没收到信"仍然有两种解释（一切正常 / cron 又没触发）。#68 之后
  我倾向于不为此加每日成功邮件（成功邮件发几天就没人看了，等于制造噪声）；更合适的是把
  "最新 dump 是否 <26 小时"变成一个可查项 —— 已留在 `deploy/audit-email-paths.sql` 之外，
  需要时再单独决定。
- 未做：磁盘写满、`/var/backups` 权限异常这类失败同样会走 ERR trap ⇒ 会发信，
  但邮件内容只有阶段与退出码，不会有 `df` 的输出。要更准就得多写日志抓取，暂不值。

## 部署与生产实测（2026-09-25，用户打字授权）

- 同步 `deploy/daily-backup.sh` + `scripts/alert-backup-failure.mjs`，`build worker` + `up -d worker`。
- **成功路径发 0 封**：手跑一次 `daily-backup.sh`，6 项恢复校验全过、新 dump 1,233,829 字节、exit 0、无告警输出。
- **失败路径真发信**：手跑 `alert-backup-failure.mjs` 一条测试告警 ⇒ 信真的出去了，`alert_sends` 由 13 行变 14 行。
- 一个当时要判断的相互作用：去重键是**站点日历日**（`siteDateIso`，按 Asia/Shanghai）× 任务名 × 源，
  所以这条测试信占掉的是"北京 9-25"那天 `daily-backup` 的额度；今晚 19:30 UTC 的自然运行是**北京 9-26 03:30**，
  跨了站点日 ⇒ 没被吃掉。反过来说：同一天内若既有测试又有真故障，真故障那封会被去重掉。
