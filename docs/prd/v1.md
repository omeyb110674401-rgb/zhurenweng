# PRD：主人翁 v1 —— 政府公示信息聚合网站

## Problem Statement

关心公共事务的普通人想参与立法和政策制定，却面临四重障碍：

1. **找不到**：征求意见稿分散在全国人大、司法部、各部委等几十个官方渠道，没有普通人会逐个查看；官方集中入口存在但知晓度低、体验差。
2. **看不懂**：法律草案原文专业艰深，普通人无法判断"这和我有什么关系"。
3. **来不及**：公示期通常 30 天左右，错过截止日期即失去参与机会，且没有可靠的提醒机制。
4. **不会提**：即使想参与，也不知道去哪里、以什么形式提交意见。

结果是征求意见稿参与人数普遍很少，公众的主人翁意识难以落地。

## Solution

**主人翁**是一个聚合网站，只做三件事，构成一条完整转化漏斗：**发现 → 读懂 → 行动**。

- **发现**：每日定时抓取国家级官方渠道的公示/征求意见稿，统一结构化入库，按截止日期排序展示，提供分类浏览与全文检索。
- **读懂**：每条公示自动生成结构化 AI 摘要，显著标注 AI 生成并附原文引用，用户可随时核对原文。摘要口径为**参与导引**：这是什么 / 影响谁 / 逾期会怎样 / 截止日期 / 如何提意见 + 可操作的提交渠道清单（邮箱、电话、邮寄地址、在线入口），并明写「具体条文在官方附件与原文里」。（2026-09-21 issue #55 修订：原口径含「关键条款」，但生产实测抓取到的正文均值仅 443 字、是公告壳，草案条文都在附件中 —— 从壳里"概括条款"只能产出看着像条款的元信息复述，故删该段；补条文需先解析附件，见 #55 的可行性数据。2026-09-22 issue #56 再修订：「影响谁」由必填降为**可缺段** —— 壳里通常不写受影响主体，必填它的实测结果是 30% 条目直接转人工复核、侥幸通过的 26/35 条填的是「有关单位和公众」这类被禁止的泛称；该段现在只在原文明确写出主体时出现。**2026-10-02 修订：删「谁能提」段** —— 生产只读实测 96 条摘要里 **95 条**的取值等价于"公众 / 社会各界 / 有关单位都可以提"（去重后 18 种写法全是同义改写，平均 10.4 字），而这**本来就是"公开征求意见"的定义**，等于用一段版面复述一个已知事实；另有 28% 是空的。「影响谁」同时收窄为**只在行业专业档渲染**（实测它的价值与受众面强相关：行业专业 84 条里 15 条有值且各不相同、条条是"这条管的就是你"，公众广域 11 条里 8 条为空、剩下的是义务主体清单）；"谁受影响"的**深度**改由 L3 判读承担 —— 判读每条自带「可能受影响」（实测 39 条判读覆盖率 100%，且与标题最长公共子串多为 0–1，即从条文判出来的而非标题复述）。**2026-10-02 第二刀修订**：判读那一段加「影响点」三件 —— 每条原来那行「可能受影响：<长串主体>」改成「影响：<主体> · <方面>」（主体 ≤20 字、单一主体类别、最多一个顿号；新增的「方面」≤12 字，回答"他的什么被动了"，如「匿名发声空间」「纠错渠道」「合规成本」—— 两者都由提示词约束，**超长值照实显示、不静默截断**，长度分布留作提示词迭代信号）；并在该块**块首**加一行**程序聚合**的概览（`共 N 处：…各类计数…` ＋ `影响：<主体列表>`，不额外调模型、不额外花钱）。旧行没有「方面」字段也照常渲染，只是少半句。）**2026-10-02 收尾修订**：① `whoCanSubmit`（「谁能提」）**整体删除** —— 它被生成、被落库、被索引，但前台早已不渲染，而复述的正是"公开征求意见"的定义本身（96 条里 95 条等价于"公众可提"、平均 10.4 字、28% 是空的）；旧摘要里那个键由读侧忽略（见 `docs/pending-issues/89-remove-who-can-submit.md`）。② **列表页 / 首页改为宽屏两栏**（断点 1000px、筛选入右栏、窄屏落回改动前的单栏顺序）：改动前 1440×900 下容器只有 760px、筛选块占掉整个首屏，**整屏只能读完 1 条**公示；改动后第一条卡上移 283px（见 `docs/pending-issues/90-list-page-two-column.md`）。**2026-10-03 修订**：**列表页标出「含本站推断（非官方）」/「含改动对照」** —— 判读与改动对照此前只存在于详情页渲不渲染，读者必须先点进去才知道值不值得读（全库 97 条摘要里只有 11 条带判读，正是这 11 条需要被看见）。标记的判据与详情页**同一道门**（经由 `shouldRenderImpacts`：行业专业档**不打**判读标记，因为那一段在详情页对 sector 根本不渲染；改动对照不受此门控，它是事实），只放首页，措辞用「推断」而不是「AI 判读」，不加物化列、不加筛选、不写进结构化数据（见 `docs/pending-issues/87-list-page-discoverability.md`）。
- **行动**：详情页显著引导"去官方渠道提意见"，并提供操作指引；邮件订阅按关键词/领域在截止前 7 天、3 天推送提醒；提供全量 RSS。

**北极星指标：出站提意点击数**（详情页 → 官方渠道的跳转次数）。本站永远不代替官方渠道受理意见，定位是引流与解读。

## User Stories

1. As a 公众访客, I want a 按截止日期排序、带倒计时的公示列表, so that 我能立刻看到哪些征求意见即将截止.
2. As a 公众访客, I want a 每条公示的结构化 AI 摘要（这是什么/影响谁/逾期会怎样/截止日期/如何提意见与提交渠道）, so that 我不啃原文也能明白它与我的关系、并知道去哪提.
3. As a 公众访客, I want a 显著标注"AI 生成"且可一键跳转官方原文的摘要, so that 我知道哪些内容是机器生成并可以自行核实.
4. As a 公众访客, I want a 醒目的"去官方渠道提意见"按钮和分步操作指引, so that 我知道下一步去哪、怎么提交意见.
5. As a 公众访客, I want a 每条记录的发布机关、发布日期与官方原文链接, so that 我能确认信息来源可信.
6. As a 公众访客, I want a 按领域/部门分类浏览与关键词过滤, so that 我能快速找到与我相关的公示.
7. As a 公众访客, I want a 覆盖摘要与原文全文的站内检索, so that 我能按主题搜索历史公示.
8. As a 潜在参与者, I want a 邮件订阅关键词/领域并在截止前 7 天和 3 天收到提醒, so that 我不错过想参与的公示.
9. As a 潜在参与者, I want a 全量公示的 RSS feed, so that 我能用自己熟悉的阅读器跟踪更新.
10. As a 关注某法案的访客, I want a 新旧版本草案的条款对比视图, so that 我能看出这次修改到底改了什么.
    > 实施修订（issue #59 记录）：**该 story 的验收口径改成「关联逻辑正确 + 随收录累积自然出现」，而不是「页面上能看到对比」**。2026-09-24 在生产容器实测 `scripts/audit-versions.mjs`（只读）：187 条里可参与匹配 186 条，严格分组 186 个**全部单成员**，放宽到按法案名分组仍是**零候选** ⇒ 线上 0 条版本链是数据实况，不是规则过严，所以"放宽关联算法"这一刀按实测撤销（它只会造出 0 条链）。要让对比真的可见只有一条路：**回填历史旧页**（同案多轮之间隔数月，当前收录窗口装不下），那是另一件事、需单独决定。在回填之前该功能对读者不可见 —— 入口只在 `versionOf` 非空时出现，所以线上不会出现坏链。重跑判据：`docker compose exec -T worker node scripts/audit-versions.mjs`。
11. As a 关心公共参与的访客, I want a 数据统计页（各部门公示量趋势、公示期长度分布等）, so that 我能看到政务公开活动的变化.
12. As a 站长, I want a 管理后台（源管理、抓取健康状态、摘要复核队列、手动补录）, so that 我能维持数据质量与管线健康.
13. As a 站长, I want a 抓取失败与摘要失败告警, so that 源页面改版导致的断流能被当天发现而不是静默腐烂.
14. As a 站长, I want a 出站提意点击统计（按条目/日期聚合）, so that 我能跟踪北极星指标.

## Implementation Decisions

### 技术栈（统一 TypeScript/Node 单仓单体）

- **Web 应用**：Next.js（App Router）+ TypeScript，服务端渲染为主（SEO 与国内访问速度优先）。
- **主存储**：PostgreSQL。
- **全文检索**：Meilisearch（中文分词开箱即用），索引字段含标题、AI 摘要、正文纯文本；由管线在入库/更新时同步。
- **爬虫 worker**：与 Web 同仓的 Node worker，优先 `fetch` + `cheerio` 解析静态页；确需 JS 渲染的源再用 Playwright（按源配置启用）。
- **AI 摘要器**：调用**已备案的国产大模型 API**（默认 GLM 系列，通过环境变量可切换服务商），输入正文纯文本，输出结构化摘要 JSON；失败重试 3 次后进入人工复核队列，详情页在摘要缺失时显示"摘要生成中"占位而非空白。
- **邮件**：国内 SMTP 服务商（阿里云邮件推送或同类）。

### 源与适配器（数据接入的唯一扩展点）

- 每个源一个**适配器**（adapter），输入 = 源页面（HTML/JSON），输出 = 标准化公示条目；新增源只新增适配器与注册配置，不改核心代码。
- **M1 源清单**：全国人大网"法律草案征求意见"列表页、中国政府网"意见征集"栏目、司法部征求意见系统（3 个官方聚合页）+ 首批 8 个重点部委直爬（发展改革委、教育部、工业和信息化部、生态环境部、住房城乡建设部、交通运输部、市场监管总局、国家网信办）。
  > 实施修订（issue #33 / #58 记录）：中国政府网"意见征集"栏目该聚合页已下线（`govcn` 适配器删除、库内死行清理），承担同一职责的是**生态环境部**直爬源（`mee`，其实测就是部委直爬口径）；当前注册表共 9 个源，清单以 `src/sources/registry.ts` 为准。
- 调度器每日定时抓取全部源；抓取与解析失败记入健康状态并触发告警（M3 起邮件告警，此前在后台可见）。

### 数据模型（核心 Schema）

- **公示条目**：标题、发布机关、源 ID、原文 URL（唯一键，防重复入库）、发布日期、截止日期、状态（征求意见中 / 已截止 / 已出结果）、领域标签、正文纯文本、附件清单、AI 摘要（结构化 JSON，每个字段附原文引用片段）、摘要模型名与版本、抓取时间、版本历史（用于条款对比）、出站点击计数。
- **源**：名称、适配器类型、调度配置、健康状态、最近成功时间。
  > 实施修订（issue #58）：**删掉「调度配置」这一列**。它存在、每次抓取被写成 `{}`、但没有任何代码读它 —— 一个看起来能按源配调度的幽灵旋钮，操作者改了毫无效果。调度间隔按部署整体配（`WORKER_INTERVAL_MS`），按源的传输要求由适配器在代码里声明（`fetch.timeoutMs` / `cookieChallenge`），因为「声明了什么」必须被代码读着、能被人看见。健康状态从「一次失败即异常」改为按**连续失败轮数**判定（新增同名列），并增加「当前错误信息 / 时间」两列（成功即清空，历史在日志与告警里）。
- **订阅**：邮箱、关键词/领域规则、确认状态（double opt-in）、退订 token。

### 出站转化埋点

"去官方渠道提意见"按钮统一走站内跳转端点（`/go/<条目ID>`）：记录点击（条目、日期，**不记录个人身份**）后 302 至官方原文。统计页聚合呈现。

### 合规姿态（不可妥协项）

- 只收录官方公开发布的信息，所有条目保留原文链接与出处。
- AI 摘要在详情页**显著标注**"AI 生成，仅供参考，以官方原文为准"，满足生成式内容显式标识要求。
- 不提供站内评论、联署等任何 UGC 功能；意见提交一律引流回官方渠道。
- 邮件订阅采用 double opt-in + 一键退订；仅存储订阅邮箱，不建用户账号体系。
- 页脚展示 ICP 备案信息。

### 分期（每期结束都是可部署的完整产品）

- **M1**：3 个官方聚合页适配器 + 调度管线 + 归一化存储 + 聚合列表（倒计时排序）/详情页 + AI 摘要 + 出站跳转端点。
- **M2**：邮件订阅 + 截止提醒（7 天/3 天）+ RSS + Meilisearch 全文检索 + 领域/部门分类浏览；部委直爬源扩展至 8 个。
- **M3**：数据统计页 + 新旧版本条款对比 + 管理后台 + 失败告警。

### 部署

国内云单机起步，Docker Compose 编排（web / worker / PostgreSQL / Meilisearch）；ICP 备案通过前不绑域名面向公众，管线在本地与 CI 验证；备案通过后绑定域名正式上线。

## Testing Decisions

**唯一测试缝：端到端管线缝。** 不写针对内部实现的单测，只从外部行为驱动整套系统：

> 实施修订（issue #82 记录，2026-09-26 核实）：**这一句只在"验收必须从 HTTP 层发出"这个意义上仍然成立**，
> 「不写单测」已经不成立了 —— 仓库现有 **39 个单测文件**（`tests/unit/`）。它们集中在三类纯函数上：
> 分类与判定规则（体裁 / 受众面 / 领域关键词）、文案与形状归一化（摘要形状、邮件文案、提醒档）、
> 以及契约（部署环境变量三方一致、迁移目录完整性）。理由是这些地方**从 HTTP 层看不见退化**：
> 一个关键词词表判错只会让某条公示挂错角标，没有任何页面级断言会因此变红。
> 端到端缝仍然是**产品行为**的唯一判据，两者分工写在这里，别再让文档与仓库各说一套。

- **Fixture**：每个源的真实页面快照存入 `fixtures/<source>/`，爬虫测试时以本地 fixture 服务替代真实源站。
- **Stub**：LLM API 与邮件发送器被 stub（LLM 返回固定摘要 JSON，邮件发送器捕获发出的邮件）。
- **断言（全部从 HTTP 层发出）**：
  - 列表页展示来自 fixture 的新公示条目，截止倒计时正确；
  - 详情页含 AI 摘要内容与"AI 生成"标注、官方原文链接；
  - 出站跳转端点正确 302 到原文且点击计数 +1；
  - RSS feed 包含新条目；
  - 截止前 7 天/3 天的提醒邮件在正确时机发出、内容含正确条目与官方链接；
  - 检索能命中 fixture 条目。
- 新增一个源 = 新增一份快照 fixture + 通过该源的端到端场景，适配器契约由场景隐式定义。

## Out of Scope

- 站内评论、讨论区、联署等任何 UGC 功能（合规负担大，且意见的法律效力在官方渠道）。
- 省级、市级源（适配器架构已预留扩展点，另立 PRD）。
- 开放数据集下载与公开 API（未来 PRD，M3 仅含统计页）。
- 微信公众号推送（二期增长渠道，另行评估）。
- 用户账号体系与商业化。
